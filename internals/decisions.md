# Decisions

A short, dated log of choices a future maintainer or agent might otherwise undo.
Add one line per decision: `Dn (YYYY-MM-DD): decision — why.` Replace a line
when a decision changes; git keeps the history.

- D1 (2026-10-06): Adopt the Lupinum OSS standard (lupinum-oss 9841872, `nuxt-module` starter) — every Lupinum repository shares one release, security and CI setup, so fixes to the standard apply everywhere. Changesets replaces changelogen and the hand-run release; the `beta` prerelease line continues in pre mode until 0.4.0.
- D2 (2026-10-06): Keep the extra CI jobs for the Node floor and newest Node, the pinned-Linux raster suite and the Windows path tests, and the packed-package consumer test (`test:packed`) — they guard behavior users rely on: supported Node versions, PDF output, Windows paths, and installing the published tarball at the lowest supported peers.
- D3 (2026-10-06): Remove `upstream-drift.yml` and the scheduled soak and compatibility runs — Renovate opens a pull request for every new `@react-pdf` version, and CI runs the conformance and raster suites on it; `test:performance` stays as a manual check.
- D4 (2026-11-12): Lay out and serialize every render in a pooled worker thread (at most min(4, cores − 1), idle workers unref'd, no module option) and terminate the worker at the deadline; Vue mounts once on the main thread and the worker gets only the plain-data tree. Builds that inline dynamic imports render the same adapter output in-process with one build warning. There is one render path: no second path for documents with page numbers or callbacks — a hard deadline and parallel renders need a tree that can cross a thread, the old checked deadline could not stop one long layout step, and one path means one place for limits, metadata and image policy. Replaces the "Worker cancellation decision" in CONTRACTS.md.
- D5 (2026-11-12): Page numbers are plain-data tokens (`PdfPageNumber`, `PdfPageCount`, `PdfPageRef`) that the engine adapter turns into per-page text; the `render` prop, `usePdfPageNumbers()`, `hyphenationCallback` and every function prop are removed (`:hyphenate="false"` keeps words whole) — a function cannot cross the worker boundary, and a token lets the layout loop resolve `PdfPageRef` numbers without mounting Vue again.
- D6 (2026-11-12): Declare every primitive once in `PDF_PRIMITIVE_TABLE` (`runtime/primitives.ts`, plain TypeScript, no validation library); components, the prop allowlist, nesting, per-prop checks, dev stubs and generated component types derive from it — separate lists drifted, and a row that disagrees with its exported props type does not compile.
- D7 (2026-11-15): Style templates with plain `<style>` blocks, compiled at build time to rules of `PdfStyle` objects: class selectors, compound (`.a.b`) and descendant (`.a .b`) selectors matched lexically inside one template, file-local variables (`:root { --x: … }`, `var(--x)`), `@import` of a local `.css` file inside the project, and `v-bind()` for a value that lives in the script — invalid CSS fails the build with file, line and column, the server bundle ships JSON instead of a CSS parser, and a value exists once. Rules apply by specificity (classes in the selector), then source order. A `v-bind()` value is read at render time and passes the same check as a `:style` value; everything else is resolved at build time. Classes never reach into another component. Not built on purpose: type selectors, `>`/`+`/`~`, pseudo-classes. (Replaces the 2026-11-12 line, which ruled `v-bind()` out: the acceptance of values duplicated between script and style was the larger cost.)
- D8 (2026-11-12): `fixed` plus `pages` (`all`, `first`, `continuation`) is the one concept for repeated content; `PdfTableHeader` is a `fixed` row — the engine already repeats a `fixed` node on every fragment of its parent in one pass (500 rows cost 0.90× a header printed once), and `pages` covers a running head from page 2 without a callback. A view whose first fragment would hold only its `fixed` children starts on the next page.
- D9 (2026-11-15): `PdfAttachment` and `PdfFacturX` take content only (a string as UTF-8 or a `Uint8Array`), never a path or URL, and the engine always receives a `Buffer` — pdfkit's `file()` reads a string, and a plain `Uint8Array`, as a server file path, so anything else could embed a server file. The author supplies the invoice XML; `PdfFacturX` only fixes the file name, the relationship and the XMP extension schema the standard requires, implies PDF/A-3b, and checks that the profile named in the XML matches its `profile` prop. No e-invoice content logic.
- D10 (2026-11-15): One document prop, `conformance` (`'PDF/A-3b'`, `'PDF/A-3a'`, `'PDF/UA-1'`, or a list with at most one PDF/A level), and a document that claims a level either validates or the render fails with a typed error — the library never writes a file that claims a standard and is not. The evidence is veraPDF from a Docker image pinned by digest (`pnpm test:pdfa`, its own CI job); nothing is claimed that veraPDF cannot check (the Factur-X XML, the human checks of PDF/UA). The ICC profile is built in code from the public sRGB constants. Tagging leans on internals of the pinned, unpatched engine (wrapped methods on our own pdfkit document, a marker object in `props.id`, the paint order of `renderNode`); each one is listed in `CONTRACTS.md` with a test that fails when an engine update changes it. A document without a claim writes the same bytes as before. (Replaces the 2026-11-12 line "do not build until a validator checks the output": the validator is there.)
- D11 (2026-11-12): Source positions (`file:line:column` on errors, layout warnings and the preview) exist in development only, behind an explicit plugin option that `/build` and `/test` leave off — production output carries no file path, and the position is a host-node field, not an engine prop, so layout and bytes stay the same.
- D12 (2026-11-12): `typescript` and `vue-tsc` are optional peers loaded lazily by `@lupinum/nuxt-pdf/build`, with an install hint when missing — only `buildPdfRegistry` emits declarations; the Nuxt module, `/test`, `/server` and the runtime never load them, and the production install shrinks from 260.5 MB to 234.1 MB.
- D13 (2026-11-15, replaced by D39): Tables have `colspan` and no `rowspan` — a spanning cell must move the rows it covers into one unbreakable group, but those rows are siblings the author renders (`v-for`, rows inside local components), so the table cannot see them; rewriting the mounted tree would be a second tree transform. If it is ever needed, the honest API is an explicit row group the author writes.
- D14 (2026-11-15): In `nuxt dev` a template that fails to compile becomes a stub that fails with `PDF_TEMPLATE_INVALID` and its source position, and adding or removing a template rebuilds the registry without a Nuxt restart; a production build still fails hard — an author fixes a typo in the preview, and a broken template can never ship. Removed props (`render`, `hyphenationCallback`) fail at build time through the same path.
- D15 (2026-11-15; the continuation-node limit removed 2026-11-25, step 7: the page builder gives a `pages="continuation"` node no room on the first page): Known limits kept on purpose, each with its cause: a border colour with alpha is rejected (the engine's border painter does not split the alpha); `PdfNote` is rejected in PDF/A and tagged documents (they need an appearance stream the engine does not write).
- D16 (2026-11-15): The render checks every `:style` and `v-bind()` value, and rejects only what the engine cannot read correctly. A string passes when it fits the `<style>` block rule of its key or the engine's own reading of that key (`ENGINE_FORMS` in `src/runtime/shared/style-values.ts`, each form confirmed by a raster comparison against the code before the check). The `<style>` block keeps its narrower grammar, and the public style types stay narrower than what passes. Reason: the first version of the check reused the build grammar and rejected values that had rendered correctly (`'transparent'`, `margin: '4 8'`, `width: 'auto'`).
- D17 (2026-11-15): Templates run in the server process; only layout and writing run in the worker. So `pdf.limits.timeoutMs` cannot stop synchronous template code such as an endless loop in `setup` (the same as for any server-rendered component). Documented in the errors and limits page and in `CONFORMANCE.md`; a worker for the Vue render is not built, because templates may use values and composables that cannot cross a thread boundary.
- D18 (2026-11-15): An unknown `<Pdf…>` tag fails the build only when the file cannot provide it: the check follows how Vue resolves a tag (a `<script setup>` binding, a `components` key in any case form, the file's own name) and accepts every tag when the options cannot be read statically (a spread, a variable, `extends`, `mixins`). A false build failure is worse than a missed typo, which still fails at render time.
- D19 (2026-11-16): Own the layout step: `src/runtime/server/engine/layout/` holds a corrected copy of `@react-pdf/layout` 4.6.1 (`lib/index.js`, 3,298 lines), and the package's runtime dependencies become our direct, pinned dependencies — the invariant harness found that the pinned package loses text (a padded box nested in a box near the page end), paginates without end (a nested `break` with a fixed node) and paints a page-number text twice; plain `@react-pdf/renderer` 4.5.1 shows the same. The page-break functions are private to the package, so no adapter seam can fix them, and `pnpm patch` does not reach applications that install us. The copy is upstream plus a short list of scripted edits (`scripts/vendor-layout.mjs`, a check fails when the committed copy differs from upstream plus the edits), so an upstream update is a re-run of the script; `@react-pdf/layout` stays as a dev dependency as the source of the copy. A rewrite of the layout step is a later, separate decision. Decided by Matthias ("Yes, own layout").
- D20 (2026-11-17): A forced `break` with no flow content before it on the page is ignored at every level, also on the first element of a page — an empty page, or a page with only fixed content, is never what an author wants, and the page-level rule then matches the nested rule that ends the endless pagination (D19). React PDF gives a blank page here; we differ on purpose. Found by the invariant harness (G2).
- D21 (2026-11-17): `PdfDocument` `protection` writes AES-256 revision 6 only (ISO 32000-2, PDF 1.7 with Adobe extension level 8), from our own standard security handler in `engine/protection.ts` (`node:crypto`) installed on pdfkit's `_security` hook; pdfkit never gets a password — the pinned pdfkit writes AES-256 only as revision 5, which ISO 32000-2 deprecates and whose password check is one SHA-256, and a fork or patch would not reach installing applications. With only `openPassword` the owner password is 32 random bytes that are not kept; protection conflicts with PDF/A and `PdfFacturX` (typed error); encrypted output is excluded from byte reproducibility, because keys or salts derived from the document would be predictable (the file ID is public). Pending the steering session's review.
- D22 (2026-11-18): Form fields (`PdfTextField`, `PdfCheckbox`, `PdfSelect`) are written by Nuxt PDF at one engine seam (`engine/forms.ts`): every field node is painted as the engine's `TEXT_INPUT`, and our `formAnnotation` writes the field dictionary and its appearance streams — the engine's checkbox paint adds a non-embedded ZapfDingbats font and its option parsers write the defects F5a found, while one seam keeps one source for every field key. The appearances use the standard font Helvetica (WinAnsi only, metrics from pdfkit's AFM data), a fixed size from the style (`fontSize`, `color`, `textAlign` inherit like text), the border and background inside the appearance and not on the page, and no `NeedAppearances`, so every reader shows the same field; a long value is clipped, never shrunk. Fields stay rejected in PDF/A (Helvetica is not embedded) and tagged documents (no Form structure element yet) until F5c. (Replaces the 2026-11-17 line, which left drawing to the reader.)
- D23 (2026-11-18): A tree validation message names the element and its `id` (`<PdfText id="intro">`), the prop or style key and the wrong value, cut at 40 characters (`pdfElementLabel`, `describePdfValue`), and never a password or the text of a node; a duplicate id names both elements. This replaces the earlier rule that the duplicate-id message must not echo the identifier: without a source position (production) the author could not find the element. Style values keep a sign rule per key (`PDF_STYLE_SIGNS`, next to `PDF_STYLE_VALUES`, one entry per key), checked by one function for `:style`, `v-bind()` and the `<style>` block. Decided by the steering session (slice V1).
- D24 (2026-11-18): A forced `break` starts a new page at every depth, also inside a container that fits on the page; the rest of each container continues on the next page as a split part, and a container whose first flow content has the break moves whole. It has no place inside a row (also a table cell), inside a `wrap={false}` node and inside a `fixed` node, and tree validation rejects it there (D26): row children sit side by side and are split at one height, so a break cannot end the page for one column only (CSS propagates a break on a row item to the row; we ignore it so a neutral wrapper never changes the result, I13); `wrap={false}` keeps its node whole, so it wins over a break inside it (CSS lets a forced break win over `break-inside: avoid`); a fixed node repeats. React PDF honors a nested break only inside a container that overflows. Found by I13 (H5-A).
- D25 (2026-11-18): Margins at a page top, the same at every depth (a neutral wrapper never changes a position, I13): a node that moves whole to the next page keeps its top margin, after an automatic break and after `break`; the continuation part of a split node has no top margin, top padding or top border of its own start; whether a node fits is decided with the same margins at every depth, so a node whose bottom margin does not fit moves at every depth, as React PDF's presence rule already did at page level, and its container moves whole when the node is its first content. CSS truncates the margin after an unforced break; we keep it, because page-level views already kept it and the old beta rendered the RC1 consumer documents with it. Before, a page-level text moved by the orphan rule lost its margin (H5-C) and a nested node never moved for its bottom margin (H5-D). Decided by the steering session. Amended 2026-11-23 (round 9, finding (r); round 10: automatic breaks only): on a page after an automatic break a negative top margin counts only down to the content top (`paginate/page-top.ts`); where the author put the node at the page top (the first page, after `break`, at any depth) it reaches above the content area, so the same component looks the same on page 1 and on a chapter page (the splitter tells the page loop that a page ended at a forced break); and in a column (not `column-reverse`) every flow child after one that starts or continues on the next page goes there too (`splitNodes`); before, a node pulled up by a margin larger than the content above it stayed on the page before the content it follows and was drawn above the next page, with the nodes after it. A positive top margin stays as it is. Amended 2026-11-23 (finding (ah)): a node's own bottom margin never moves it; a node whose box fits stays and loses the margin at the break, at every depth and in columns, as CSS truncates a margin at an unforced break, and `minPresenceAhead` still counts from the end of the margin. The move kept the old beta's output, but it left up to a node's height empty at a page or column end for a reason authors could not see.
- D26 (2026-11-22): Tree validation rejects `break` (when true) on a node inside a row (an ancestor whose resolved `flexDirection` is `row` or `row-reverse`, the page included), inside a table row or cell, inside a `fixed` node and inside a `wrap={false}` node, with `PDF_TREE_INVALID`; the row itself, a table row and a `wrap={false}` node keep their own `break`. The message (D23) names the element, the outermost ancestor that prevents the break (removing an inner one would not make it work) and what to do: put `break` on the row or table row, remove `wrap={false}`, or remove `break`. Before, the layout ignored such a break silently (D24), so an author saw no page break and no reason; the layout keeps ignoring it as a second line of defence. D20 stays: a `break` with no flow content before it on its page is still ignored, because it is valid where it stands. Decided by the steering session (E4). The feature branch also used the number D24 for another decision; renumber that one when the branches meet.
- D30 (2026-11-22): A line of text is broken at its natural width. A line that is not justified (left, right, center, and the last line of justified text) is never squeezed or stretched: its glyphs keep their shaped advances plus `letterSpacing`. Justified text may stretch spaces (and then letters) on every line but the last, and never shrinks them, so the line ends at the box edge. A line never ends past its box, unless it holds one token wider than the box with no break point (no space, no hyphenation point); that token keeps its natural width and overflows the box to the right, visible and not cut (as CSS `overflow-wrap: normal`). Before, the line breaker gave every space a shrink of a third of its width for every alignment, the justification step could take back only 11/128 pt per glyph, and the paint step squeezed every line that was too wide, also left-aligned text, so a line in a monospace font ended up to 7 pt past its box (W1-A) and 16 to 29 % of the lines in the probe fonts were squeezed. Browsers do the same: justification only grows. Line breaks move in existing documents. Decided by the steering session. D27 to D29 are used on the feature branch.
- D27 (2026-11-18): Rich text has one model (`PdfRichBlock[]`, plain JSON data in `src/runtime/rich-text/types.ts`) and every input becomes it before the render: HTML through our own one-pass parser in two steps (a plain `[tag, attributes, ...children]` tree, then one mapping with the allowlist and the limits, which F2b feeds comark's tree into), a project's CMS JSON through its own mapping to `content`. `PdfRichText` styles its elements through a typed `styles` prop merged over defaults that scale with its own `fontSize` — classes compile into `$nuxtPdfClass` calls in the author's template, so nodes a library component builds with `h()` never take part, and a second class mechanism would be a second styling route. Links keep only absolute `http:`, `https:`, `mailto:` and `tel:` targets; the HTML adapter drops other links and keeps their text, a model fails. Limits (1,000,000 characters, 50,000 nodes, depth 32, measured against the longest docs page: 47,775 characters, 3,910 elements, depth 5) and model errors fail with the new code `PDF_RICH_TEXT_INVALID` and `issues` (`PDF-RICH-NODE`, `PDF-RICH-LIMIT`) whose messages name the path and the value, never the article text (D23).
- D28 (2026-11-21): Markdown and comark input feed the one rich text mapping of D27; there is no second model or renderer. comark is an optional peer (`^0.9.2`, tested with 0.9.2), loaded with a dynamic import only by `parseRichTextMarkdown`; a missing package fails with `PDF_RENDER_ERROR` and the install command, because it is a setup error, not an input issue. comark parses only asynchronously and templates cannot await (async setup is rejected), so there is no `markdown` prop: the route awaits `parseRichTextMarkdown` and passes the model to `content`, and the function is not auto-imported in templates. A Promise given to `PdfRichText` gets its own message. The `comark` prop takes an already parsed document without the package; its shape is checked first with paths (D23). Tags that are not HTML element names become `component` blocks (`name`, JSON-only `props`, `children`, named `slots`), only from comark and Markdown and only at block level (root, quote, another component); the `components` prop maps exact names (comark's kebab case) through a `Map`, and an unmapped component prints its slots and content without a wrapper. A mapped component gets only the props it declares (its `props` list or object, with `extends` and `mixins`, compared in camelCase; `key` and `ref` never), the rest are dropped without an error, so content cannot set listeners, Vue's own props or attributes that fail on the root primitive; the model keeps every prop. Markdown has its own limits, checked before the parse: 250,000 characters and 20 `<!--`, because comark parses on the event loop and is quadratic on comments; deeply nested quotes stay slow (seconds) and need a time bound that is not built yet (replaced by D29: the comment limit is gone, the parse runs in the worker with a time limit). Every lookup of an input string uses a `Map`, a `Set` or `Object.hasOwn`.
- D29 (2026-11-22): Untrusted rich text must never block or slow the server, and a pre-check per slow comark pattern is a list that never ends (quote depth 100: 1.3 s; depth 60 with 20 comments: 7.7 s; 250,000 characters of `<!--`: 16 s). So `parseRichTextMarkdown` sends the Markdown to the render worker pool: the worker imports comark, parses, runs `mapComark` and returns the model. The Markdown parse is a second request kind of the worker protocol on the same pool path (`runInWorker`: FIFO wait, hard deadline with a terminated and replaced worker, failure path, retirement count), not a copy. Its deadline is `pdf.limits.markdownTimeoutMs` (default 5,000 ms: a 100-page article takes about 0.1 s in a warm worker and 0.5 s with a cold start under load, so about 8x room), the wait for a worker included like `timeoutMs`, and `#pdf` binds the configured value; a call can pass `{ timeoutMs }`. Over it: `PDF_LIMIT_EXCEEDED` naming the option. The `<!--` count limit is removed; the 250,000-character limit stays, because the default time limit is sized for the longest honest input and a shorter input keeps it, and with it the time a hostile request holds a worker, short. No in-thread fallback: a build without a worker chunk (a Nitro preset that inlines dynamic imports) fails with `PDF_RENDER_ERROR`.
- D31 (2026-11-22): Form fields in a PDF/A document (and, since F5c part 3, in every document with a `conformance` level: PDF/UA-1 also requires embedded fonts, veraPDF 7.21.4.1-1) draw their value in the field's own registered font (the first registered family of its resolved `fontFamily`, with its weight and style; the page font when the field sets none), written as a simple TrueType font with `WinAnsiEncoding`, `FirstChar 32`, `LastChar 255`, `Widths` from the font, and the whole font file as `FontFile2`; `DA` and `DR` name it (`/FF1`), so a reader that draws a typed value again (pdf.js does it from `DA`) uses an embedded font and keeps the file PDF/A. Not a subset: the user may type any WinAnsi character later, and fontkit's subset has no cmap, which a nonsymbolic TrueType font needs to map codes to glyphs. Not a Type0 font: pdfkit's Identity-H subset has no glyphs for later input, and readers redraw simple WinAnsi fonts most reliably. Values stay WinAnsi-only as in D22. Typed errors at the field: no registered font (Helvetica), a font with CFF outlines or without a (3,1) cmap, and a value or choice character the font lacks. The layout step resolves the font (`resolveFieldFonts`), because serialization has no font store. Without a PDF/A level nothing changes (Helvetica, D22). `PdfFacturX` with fields stays an error: a reader could change what the invoice shows while its XML stays. Cost: the whole font file once per field font (Roboto 168 KB).
- D32 (2026-11-22): In a tagged document (PDF/UA-1, PDF/A-3a) each form field widget is the one kid (an `OBJR`) of its own `Form` structure element, placed where the field is in the template (tree order, like every element), with `StructParent` on the widget and `Tabs /S` on the page; a radio option is a widget, so each option is its own `Form`. The `label` is required (typed error) and written twice: as the widget's `TU` (the accessible name readers use) and as `Alt` on the `Form` element, because a radio group's field is the parent of its widgets and has no `TU` of its own, and veraPDF PDF/UA-1 7.18.1-3 then asks for `Alt` on each widget's element. No group-level name: there is no group element to carry one, and the visible question is a `PdfText` read before the options. Widgets are predicted by the same annotation plan as links and tagged in an `annotate` wrap (CONTRACTS.md "Tagged PDF"), so a widget the plan did not expect fails closed. A field inside a `decorative` node or a figure view fails validation (it would be outside the reading order).
- D33 (2026-11-22): A rich text image (`PdfRichImage`, from `img`, `figure` with one `img` and a `figcaption`, Markdown `![alt](src)` and comark `img`) renders as an ordinary `PdfImage` and resolves through the one image path (`resolvePdfImageAssets`): no second resolver, nothing new reaches disk or network. A refused source (`PDF_ASSET_BLOCKED`, `PDF_ASSET_INVALID`) does not fail the render by default: an editor's broken link must not take the PDF down. `PdfRichText` renders a placeholder (a box with the alt text) after each image, and resolution keeps one of the two per image and adds a content-free entry to the new `diagnostics.imageWarnings`; `brokenImages="error"` fails with the asset error prefixed with the model path. Limits (`PDF_LIMIT_EXCEEDED`), deadlines and aborts fail in both modes: they are the server's budget, not the editor's content. Not `PdfLayoutWarning`: that comes from layout in the worker with a page and heights, while the fallback happens before layout on the main thread, and a union would break readers of `nodeHeight`. An image takes the column width without a size (the engine sizes images by the space they get, not their pixels), keeps a plain-number `width`/`height` (no CSS) with `objectFit: 'contain'`, and never exceeds the column (`maxWidth: '100%'`). In tagged documents an image without alt fails with the model path, following the `PdfImage` rule; a captioned image is one `Figure` with a `Caption`. The Markdown title, a link around an image and an image in a heading or code block are dropped.
- D34 (2026-11-22): The docs template gallery (`docs/content/docs/28.gallery.md`) is generated from the playground templates by `scripts/docs-gallery.mjs` and never edited by hand: the page embeds each template file whole (Ginko 0.16.4 has no file include) and links its local imports, and the page images are rendered from the templates with their sample data and the raster tooling of the raster tests (pdfjs-dist 6.2.108 on @napi-rs/canvas 0.1.97), page 1 at 900 px, WebP quality 80. The drift check in `pnpm test:docs` (`--check`) does not render: it compares a hash of each template's inputs (the file, its relative imports, the asset files it names, `playground/nuxt.config.ts`) and the sha256 of each committed image with `scripts/docs-gallery.lock.json`, and the page text with the generated text. Rendering in the check would make it depend on the platform's font rasterizing (macOS and the Linux CI give different pixels) and on time. Cost: an engine change that alters the paint of an unchanged template does not fail the check; the raster suite guards paint output.
- D35 (2026-11-22): Every configured limit is checked once, where it is read (`normalizePdfLimits` for `pdf.limits`, `normalizeRemoteAssetPolicy` for `pdf.remote.timeoutMs`, `parseRichTextMarkdown` for its own `timeoutMs`), by one function (`checkLimitValue`, `src/runtime/shared/limit-range.ts`): a whole number from 1 to the limit's maximum, else `TypeError` naming the option and the range. A time limit goes up to 2,147,483,647 ms (`MAX_TIME_LIMIT_MS`), the longest wait Node's `setTimeout` honours; a longer one fired after 1 ms and failed every render (X1 finding 2). Counts and byte totals go up to `Number.MAX_SAFE_INTEGER`: they are only compared with what a render uses. A value outside the range fails instead of being clamped, because a silent clamp hides a configuration mistake. There is no "no limit" value: about 24.8 days is no practical bound for a render, and no user has asked to switch a limit off.
- D36 (2026-11-22): Own the text layout like the layout step (D19): `src/runtime/server/engine/layout/textkit.js` and `textkit.d.ts` are a copy of `@react-pdf/textkit` 6.3.0 (`lib/textkit.js`, `lib/index.d.ts`) plus scripted edits, written by the same script (`scripts/vendor-layout.mjs`, separate edit lists, one `--check` in lint), and the layout copy imports it instead of the package. The D30 fix lives in private functions of the package (`getNodes`, `computeCost`, `justifyLine`), so no option or adapter can reach it. The copy's own imports (`bidi-js`, `hyphen`, `unicode-properties`, `@react-pdf/fns`) are direct, pinned dependencies; `@react-pdf/textkit` stays pinned as the source of the copy. The unedited copy gave byte-equal PDFs for 300 generated documents before the first edit. Amended 2026-11-23 (E3 slice S6): the copy is replaced by our TypeScript port in `src/runtime/server/engine/text/`; `textkit.js`, `textkit.d.ts`, `scripts/vendor-textkit.mjs` with its lint step, the text oracle and the dependencies `@react-pdf/fns` and `@react-pdf/textkit` are gone. The oracle found no difference between the port and the copy on the suite and the invariant harness before the cut, apart from its deliberate fixes. As for the layout (D38), an upstream textkit fix is ported by hand with a test that fails without it.

- D49 (2026-11-25, column, spanning and page floats, page-builder session; accepted by the steering session, 2026-11-25; full scope, with spanning floats and rich text, asked for by Matthias the same day): A node with the style key `float: 'top' | 'bottom'` leaves the flow and is placed at the top or the bottom of its reference area, as in the CSS GCPM page floats draft and LaTeX's `[t]` and `[b]`. Default `'none'`, not inherited. The contract:
  - **Reference area.** In a column container: the column the node would have started in. A float with `columnSpan: 'all'` that is a direct child of the container, or a float inside a plain child with `columnSpan: 'all'`, is a spanning float: its area is the container's part on that page, across all its columns. The part's top is where the container starts on that page. Its bottom is the page end while the container goes on to the next page, with flow or with a float that waits; on the page where the container ends, it is the container's bottom with a `height`, and right below its last content otherwise (the bottom of the balanced columns; a `maxHeight` alone gives the box the height of its content). A page with `columns` is a column container: its spanning floats go to the page top and bottom. Without columns: the page content area. We do not add GCPM's `float-reference`: `columnSpan` already says "across the columns", and one key fewer is one rule fewer; `float-reference` can come later without a break. `float: 'left' | 'right'` (CSS's side floats) fail as any other unknown value; the message lists the accepted values.
  - **Placement**, for each area (one column on one page, the page flow, or a container's part on a page), in source order. Each direction has its own queue. At the start of an area, the queued floats of each direction are placed first, in order, as long as each fits in the room left. Then the flow fills the area. A float in the flow whose queue is empty is placed in this area when it fits next to the content placed so far, and when the area, filled again with the float in it, still holds the float's place in the flow (its anchor). Otherwise it is queued for the next area, and the text after it keeps flowing in this area. A float never goes to an area before the one that holds its anchor, and never overtakes a float of its direction. When the flow ends, the queued floats are placed in the next areas of the same container (more columns, more pages); they never move into the next `PdfPage` element or out of their container. We do not adopt LaTeX's float fractions (`\topfraction` and so on): an area may hold only floats, as a LaTeX float page does. Reason: one rule, no hidden numbers; an author who wants more text per page makes the figure smaller.
  - **One queue per side in a container.** A container's spanning floats and its column floats share one queue per direction, so a numbered column figure never prints before an earlier spanning one, or after a later one. On a page the spanning top floats print above the column top floats, and the spanning bottom floats below the column bottom floats. To keep source order in that reading order: a spanning top float waits for a later page while an earlier column top float of the container is not placed yet; a spanning bottom float waits while an earlier column bottom float waits; and after a spanning bottom float is placed or queued on a page, no later column bottom float goes on that page. LaTeX had the same two queues for `figure*` and `figure` and let them cross until `fixltx2e`; we keep them in order from the start. The cost is a page that holds a waiting spanning float alone, in a rare case (an earlier column float that waits for the last page).
  - **Anchors of spanning floats.** A spanning float's anchor is a place in the galley: the number of flow pieces of the container before it. A spanning float does not end the columns: the segments around it are one galley for the fill (`joinedSegments`), so the text runs on in the same columns below or above it. A float whose anchor the part does not reach goes back into the galley at that place, cutting the rest of the segment there (`segmentAt`). A container that fits whole on a page is arranged with its floats (`withSpanningFloats`); when its fill holds a float back for the next page, the container splits where it would have fitted.
  - **Mechanics.** A top float is a piece placed at the top of its area, below the fixed nodes that repeat there (the page head, a galley's repeated rows). A bottom float is the last piece of its area: the fill runs to the area end less the bottom floats, and the first bottom float gets the free room above it as its top margin. So it sits at the area's bottom, above the footnote area and above a fixed tail that follows the flow. In a balanced part, "the bottom" is the bottom of the balanced columns: each balancing try fills its columns with the same float rules, so floats are content of the column they land in. Placing a float costs one more fill of its area; a queued float costs none. The page layout is still one yoga layout per page and the check against the summed tops still holds: the builder puts the float into the page's children where it is drawn. A float keeps the width and the left edge it had in its source place, also when it leaves a padded view. No text runs beside it. The rowGap of the reference list applies between floats and flow, as yoga puts it between all children. A spanning float never shrinks in a container with a height: it keeps its own height, and the columns get the rest.
  - **Floats inside sections.** In the paper template the figures sit in a section view (`tag="section"`, an id and a bookmark) inside the column container, not directly in it. So a float may also sit inside plain views between it and the page flow or the column container: views in column direction that can split, with no `height`, `minHeight`, `maxHeight`, `flexGrow`, `justifyContent` other than `flex-start` or reverse direction, and that are not a link, a row, a table part, `fixed`, absolute or `wrap={false}`. Before pagination each such ancestor is split at the float, as at a page break, and the float becomes a piece of the reference list between the two parts. The parts sit edge to edge (no margin or gap between them, and no top or bottom edge at the cut), so a section with a border or a background looks whole. The first part keeps the id and the bookmark; an empty part is dropped, and its id and bookmark go to the next part. The structure of the section is planned before the split (`STRUCTURE_PROP`), so both parts stay one `Sect`. The alternative, floats only as direct children, would make the paper drop its sections: no `Sect`, and the bookmarks and ids move to the headings.
  - **Rich text.** `PdfRichText` floats its images through `styles.image`, which styles every image and figure of the content, and a mapped component through its own styles. The content itself cannot ask for a float: the HTML sanitizer drops `style`, `class` and `data-*` by design, so CMS content stays content and the template decides the layout; the Markdown and comark models have no float field. A float per image would need a new content field, which no user has asked for. An image in a list item cannot float, because the item's content stands beside its marker: mount fails with a message that names `<PdfRichText>`, the image's content path and `styles.image`, and says to remove the float or move the image out of the list.
  - **Allowed nodes.** `PdfView`, `PdfImage`, `PdfSvg` and `PdfTable`, in the flow of a page or a column container, directly or through the plain views above. These fail at mount with `PDF_TREE_INVALID`: a float on a `PdfText` (wrap it in a view), in a float, in a row, in a table cell, in a fixed or absolute node, in a link, in an ancestor that is not plain (as above), in a node with `wrap={false}`, on a `PdfPage` with `wrap={false}` or `justifyContent`, a float that is or holds a column container, and `float` with `break`, `keepWithNext` or `minPresenceAhead` on the float itself.
  - **Too high.** A float never splits. A float higher than the most room its area gets on a page fails with `PDF_LAYOUT_ERROR`, worded like the error of fixed content that fills the page: "A `<PdfView>` at pdfs/paper.vue:40:5 with float \"top\" is 520 pt high, but its column has 480 pt for content. A float does not split: make it lower, or remove float so it breaks with the flow." The room is the content area less the fixed nodes that show on every page, for a column also less its galley's edges and repeated rows, and in a container with a `height` or `maxHeight` that height less its edges. So every float fits an empty area, and the queues always drain. A container with a `height` whose content and floats need more than its columns hold fails with the existing column height error, as without floats.
  - **Flow rules.** For the flow, a float is not there. `keepWithNext`, `minPresenceAhead`, the keep chains, widows and orphans, `break` on the next node and the margins of its neighbours behave as if the float were absent from its place: a heading before a float keeps with the paragraph after it. An area with floats has less room for the flow; nothing else changes. Floats are content of their area: a forced break right after the top floats is taken there, so that area holds the floats only. The pagination-stuck check counts a page that places a float as a page that places something.
  - **Column balancing.** As above: balancing tries the heights it tries today, and each try places floats by the same rules. A try that leaves a float queued is a try that leaves content, so it fails, and a higher one is tried; when no height holds everything, the part fills in order as today.
  - **Footnotes.** A note goes to the page where its mark is printed, so a mark inside a float takes its note to the float's page. Each try of the note fit fills again with floats, so the area and the floats stay consistent. A float whose note does not fit the page waits, as a float that does not fit: the fit then fills the page once more to the room its notes leave, with only the floats that fit with their notes, so the flow fills the page and its bottom floats reach the end (`fitNotes`, `Context.only`). Without that fill the page would end where the waiting float's note would have started.
  - **Reading order and tags.** The structure tree keeps source order: its indices come from the planner's counter in tree order (`tagged.ts`), and the writer sorts by them. The float is only drawn earlier on the page. The figure's alt text and its `Figure` element do not change. veraPDF PDF/UA-1 and PDF/A-3a must pass on a tagged float document in `test/pdfa.test.ts`.
  - **Destinations, PdfPageRef, outline, PdfContents.** An id on a float or in it points at the place where the float is printed, so a `PdfPageRef` prints that page. The table of contents is built from the template, so it is in source order already. The outline nests by the parent's source index at the end of the render and sorts siblings by source index, so the outline, the contents and the reading order agree; without floats this changes only a bookmarked absolute node the builder moves to a later part, which now keeps source order too.
  - **Passes.** Floats add no pass. Placement depends only on the measured heights, so the passes that exist (the reserve digits of page tokens, an orphaned table header) place them the same way; a page reference that moves a float settles, or ends at the pass cap with the typed error.
  - **Invariants** (I28, `test/invariants/floats.ts`): every word and note prints once; the flow's words keep source order; each float lies in its area, at its top or bottom edge with no flow of its area between it and that edge, and overlaps no flow and no other float; a spanning float spans the columns, lies in its container's part on its page, starts at the part's top or right below another spanning top float, and in a part that goes on ends at the page end or right above another spanning bottom float; the floats of one side keep source order, read by page, with the spanning top floats before the column ones and the spanning bottom floats after them; no float is in an area before the area of its anchor, and no spanning float on a page before its anchor's; the note of a mark in a float is on the float's page; a heading keeps with the next flow word.
  - **Cost.** About 450 lines in `paginate/builder.ts` (the area fill with its queues and refills, the container fill with the shared queue, merged segments and the cut at an anchor), 200 in `paginate/floats.ts` (the split of plain ancestors, the order numbers, the too-high check), 110 of mount checks. The work counter `floatFills` counts the fills with one float more; a page without floats pays no walk and no fill more.
  - **As built (2026-11-25).** Choices made while building, which refine the parts above: (1) The bottom float's free room is a numeric top margin, not `marginTop: 'auto'` and `spread`: the same place, and it works in a column without stretch math. (2) Where the split of a plain view at a float joins pieces of different children, the second gets the view's rowGap less the list's as top margin, so the content keeps its spacing; at a page top that margin stays (0 in the usual case of rowGap 0). (3) The too-high check is static, before pagination (`checkFloatRoom` in `paginate/floats.ts`). A float under that limit that still fits no area (fixed content on some pages only) ends in the existing typed `paginationStuck` error, never a loop. (4) The order of floats is a number in tree order, set before the hoist (`FLOAT_ORDER_PROP`); a container's fill passes a gate per side to its columns (`Context.gate`), and a column float above the gate queues. (5) The column rewrite gives a spanning float `flexShrink: 0`, as its segments have: yoga would otherwise take a container's overflow out of the float. (6) Two builder bugs the float invariants found, which also hit documents without floats, are fixed in their own commit: an empty view whose top edges do not fit a column end moves whole, and its edges count in the note fit. (7) The I28 keep check leaves out only what the keep rules allow: a chain that starts first in its area (a move gains nothing, I26), a heading before a section of floats alone (it keeps with that section's frame, which stays in the flow and holds no token), and, after a `PDF_KEEP_IGNORED`, a chain through a whole section that ends in a heading (such a chain can be higher than a page). The older gap it once skipped, a container's last child whose keep was dropped when only the container's bottom edges crossed the area end, is fixed in the page builder: such a container splits before its tail or moves whole, as one that fits.
- D50 (2026-11-25, steering session; Matthias chose "both before release"): `textWrap: 'pretty'` (the CSS name, inherited, default `'wrap'`) adds demerits in Knuth–Plass: 1e8 for two hyphenated lines in a row, 5e7 for a hyphen on the line before the last, 5e7 for a last line under a sixth of its line length. TeX's values (10,000, 5,000) changed 1 of 162 justified test paragraphs, because this breaker's badness reaches 6,400 at tolerance 4 against TeX's 200; ×10,000 avoids 56 of 60 bad endings (justified, Lora 9.5 pt, widths 140–300 pt) for +0.38 pt on the widest word gap, worst gap unchanged; ragged 20 of 20. The demerits depend only on the two breaks of a line, so the settled-line pruning stays exact. Opt-in, so no existing output changes; `hyphenateLimitChars` left out (no case needed it).
- D51 (2026-11-25, page-builder session, from the steering session's rule for the row bug the design session found): A row breaks only where every cell whose first content fits before the break by its place in the whole row shows some of it there. A cell that its own rules move after the break (a text whose orphans or widows do not fit, a node that does not split) makes the whole row move, below other content; at the top of an area it moves alone, as before. A cell that the row's layout places below the break (an alignment, a justified cell, a margin) starts there by right and does not move the row: that is the layout the author asked for (`test/engine.test.ts`, "aligns a cell of a row", and `test/corpus/pagination.test.ts`, "a row child below the page end", keep it). The steering rule as worded ("every cell with content after the break also has content before it") would also move those rows; narrowed to the cells their own rules move, it fixes the reported case (a reference number left alone at a column end) without changing aligned rows. `test/columns.test.ts`, "rows at an area end".
