Nuxt PDF renders on Node. The engine, the templates, and the embedded assets
live in the Nitro server output. The client bundle contains none of them.

## Pick a runtime

| Runtime | Support | Notes |
| ------- | ------- | ----- |
| Node server (default Nitro preset) | Supported | The tested path. Use it for high-volume or large documents. |
| Serverless functions | Supported | Works on presets such as Vercel or Netlify functions. Read the bundle and timeout notes below. |
| Edge workers | Not supported | The engine needs Node APIs. Do not target edge presets. |

## Size the memory budget

One render holds the document tree, the laid-out pages, and the output bytes in
memory at the same time. Give each function or container headroom above your
largest expected document:

- Start from `pdf.limits.maxOutputBytes` (64 MB by default) plus the tree and
  image budgets.
- Lower `pdf.limits.maxPages` and `pdf.limits.maxOutputBytes` to cap the worst
  case for untrusted input.
- Load-test with your real templates before you pick an instance size.

## Align timeouts

The render deadline lives in `pdf.limits.timeoutMs` (30 seconds by default).
The platform timeout must stay longer than that budget, or the platform kills
a render that Nuxt PDF would have finished.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  pdf: {
    limits: {
      timeoutMs: 10_000,
    },
  },
})
```

Set the platform function timeout to at least the same value plus queueing
headroom.

## Cache completed renders

A render is deterministic for one template and one props object. Treat the
bytes as a pure function of the input and cache them:

```ts [server/api/invoice.get.ts]
import { createHash } from 'node:crypto'
import { pdf } from '#pdf'

const cache = new Map<string, Uint8Array>()

export default defineEventHandler(async (event) => {
  const query = getQuery(event)
  const key = createHash('sha256')
    .update(JSON.stringify(query))
    .digest('hex')

  const cached = cache.get(key)
  if (cached) {
    setHeader(event, 'content-type', 'application/pdf')
    return cached
  }

  const result = await pdf.invoice.render({
    /* props from the request */
  })
  const bytes = await result.toUint8Array()
  cache.set(key, bytes)
  setHeader(event, 'content-type', 'application/pdf')
  return bytes
})
```

For production caches, store bytes in Redis, an object store, or a CDN behind
an ETag keyed by the props hash. A cache entry holds no request data beyond
the props you put in, so a shared cache is safe when the props contain no
secrets.

## Queue long documents

A 200-page report can occupy a worker for seconds. Keep that work off the
request path when you can:

1. Accept the request and return a job identifier.
2. Render in a background worker.
3. Store the bytes and let the client poll or subscribe.

This pattern also keeps interactive routes responsive while batch jobs run.

## Serverless notes

Serverless deploys work because every local font and image travels inside the
server bundle as validated bytes. Keep these points in mind:

- **Bundle size.** Every font and image under `pdfs/` adds to the bundle.
  Remove assets that no template uses; the module embeds only discovered
  files.
- **Cold starts.** The first invoke parses the bundle. Fewer embedded assets
  mean faster cold starts.
- **Concurrency.** Each concurrent invocation renders in its own isolated
  context. Renders never share state, so parallel invokes are safe.
- **Filesystem access.** Templates read no files at runtime. Do not add code
  that reads from the deployment filesystem during a render.

## Monitor renders

Every render returns content-free diagnostics: duration, byte length, page
count, layout passes, and registered font faces. Log them next to your request
logs to spot slow or oversized documents before users do.

```ts
const result = await pdf.invoice.render(props)
console.info('invoice rendered', result.diagnostics)
return result.response()
```
