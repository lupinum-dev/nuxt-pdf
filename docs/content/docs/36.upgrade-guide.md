This page is for an application on `0.4.0-beta.6`, the last published beta.

<!-- changeset: stable-1-0 -->
Version 1.0.0 is the first stable version. It holds every change on this
page and no other breaking change. From 1.0.0 on, a breaking change comes
only in a new major version.

Nuxt PDF now builds one plain-data document tree and lays it out in a worker
thread. A prop cannot hold a function any more, and some checks are stricter.

Work through the page in order:

1. Fix the errors at build time. Run `nuxt build` or `nuxt dev`.
2. Fix the errors at render time. Open each template in the `/_pdf` preview.
3. Check the layout changes that come without an error.

Each later section applies only when a template uses that feature.

## Errors at build time

The build names the path of the file, the line and the column of each error:

```text
[nuxt-pdf] /app/pdfs/invoice.vue:12:7 Unsupported prop "render" on <PdfText>. Use <PdfPageNumber /> and <PdfPageCount /> inside the text. Use pages="first" or pages="continuation" on a fixed text to show it on some pages only.
Also at 31:9: Unsupported prop "hyphenation-callback" on <PdfText>. Words split only at their soft hyphens, unless the style key hyphens: "auto" splits them by the patterns of the document language.
```

One error lists every removed prop of the file, so you can fix them in one
round.

<!-- changeset: change-page-number-components -->

### Page numbers: the `render` prop

The `render` prop of `PdfText` is removed. Page numbers are components:
`PdfPageNumber` and `PdfPageCount` inside the text.

```text
Unsupported prop "render" on <PdfText>. Use <PdfPageNumber /> and <PdfPageCount /> inside the text. Use pages="first" or pages="continuation" on a fixed text to show it on some pages only.
```

Before:

```text
<PdfText fixed :render="({ pageNumber, totalPages }) => `Page ${pageNumber} of ${totalPages}`" />
```

After:

```vue
<PdfText fixed>Page <PdfPageNumber /> of <PdfPageCount /></PdfText>
```

A callback that returned `''` on some pages becomes `pages` on the `fixed`
text. For a head that is empty on page 1:

Before:

```text
<PdfText fixed :render="({ pageNumber }) => pageNumber > 1 ? `${title} · ${pageNumber}` : ''" />
```

After:

```vue
<PdfText fixed pages="continuation">{{ title }} · <PdfPageNumber /></PdfText>
```

`pages="first"` shows the text on the first page only.

- A `PdfText` inside a `fixed` `PdfView`, such as a footer row, needs no
  `fixed` of its own.
- Where the callback built the whole line in JavaScript, keep the computed
  part in `{{ }}` and put the token after it:
  `{{ parts.join(' · ') }} · Page <PdfPageNumber />`.

See [Fixed content and pages]($docs.page-breaking#fixed-content-and-pages).

### `usePdfPageNumbers()`

`usePdfPageNumbers()` is removed. Print the page of a destination with
`PdfPageRef` inside a `PdfText`. The number is resolved after layout.

```text
usePdfPageNumbers() was removed. Print the page of a destination with <PdfPageRef to="id" /> inside a <PdfText>.
```

Before:

```text
const pages = usePdfPageNumbers()
<PdfText>Results {{ pages.get('results') }}</PdfText>
```

After:

```vue
<PdfText>Results <PdfPageRef to="results" /></PdfText>
```

See [Contents, links, and bookmarks]($docs.contents-links-bookmarks).

<!-- changeset: change-hyphenation-by-language -->

### Hyphenation: `hyphenation-callback`

`hyphenation-callback` is removed. Delete it: words now stay whole unless the
style sets `hyphens: 'auto'` (see Hyphenation under
[Changes without an error](#changes-without-an-error)). Custom split rules are
not supported.

```text
Unsupported prop "hyphenation-callback" on <PdfText>. Words split only at their soft hyphens, unless the style key hyphens: "auto" splits them by the patterns of the document language.
```

Before:

```text
<PdfText :hyphenation-callback="word => [word]">Donaudampfschifffahrtsgesellschaft</PdfText>
```

After:

```vue
<PdfText>Donaudampfschifffahrtsgesellschaft</PdfText>
```

### Unknown `<Pdf…>` tags

An unknown `<Pdf…>` tag now fails the build with the nearest known name.
Before, it failed only when that tag rendered.

```text
Unknown component <PdfTxt>. Did you mean <PdfText>? PDF templates can use the Pdf components of @lupinum/nuxt-pdf and components they import.
```

Correct the name, or import the component.

<!-- changeset: change-module-options -->

### Removed `pdf.limits` keys

A removed key fails module setup with a message that says what to set:

```text
pdf.limits.maxImageBytes was removed: there is no per-image cap any more. Set pdf.limits.maxTotalImageBytes, the budget for all images of one render (default 32 MiB).
```

| Removed key | Change |
| ----------- | ------ |
| `maxImageBytes`, `maxImagePixels` | Remove them. `maxTotalImageBytes` and `maxTotalImagePixels` are the budget for all images of one render. |
| `maxTreeDepth`, `maxTextCharacters`, `maxImages`, `maxOutputBytes` | Remove them. |
| `maxRemoteConcurrency` | Remove it. Remote requests run at most four at a time. |

`pdf.limits` has eight options: `timeoutMs`, `markdownTimeoutMs`, `maxPages`,
`maxNodes`, `maxTotalImageBytes`, `maxTotalImagePixels`, `maxRemoteRequests`,
and `maxTotalAttachmentBytes`. See [Errors and limits]($docs.errors-and-limits).

<!-- changeset: change-module-options -->

### Time limits above 2,147,483,647 ms

`pdf.limits.timeoutMs`, `pdf.limits.markdownTimeoutMs`, `pdf.remote.timeoutMs`
and the `timeoutMs` of `parseRichTextMarkdown` now fail above 2,147,483,647 ms
(about 24.8 days), the longest wait a Node timer allows:

```text
pdf.limits.timeoutMs must be a whole number from 1 to 2,147,483,647 ms, found 4294967296.
```

A larger render or Markdown limit failed every render after 1 ms before, so a
working project has none. A larger `pdf.remote.timeoutMs` worked, because the
render time limit bounds each request: lower it to `pdf.limits.timeoutMs` or
less. There is no value that turns a limit off.

<!-- changeset: change-module-options -->

### Unknown keys in `pdf`

A key in the `pdf` options of `nuxt.config` that the module does not read,
such as a misspelled `font`, did nothing. Module setup now fails:

```text
pdf.font is not supported. The pdf options are fonts, limits, remote.
```

Correct the key's name, or remove it.

<!-- changeset: change-one-render-path -->

### Standalone build peers

A project that calls `buildPdfRegistry()` from `@lupinum/nuxt-pdf/build` must
install `typescript` and `vue-tsc`. Without them, the build stops with an
error that names the missing package.

```bash
pnpm add -D typescript vue-tsc
```

A Nuxt project that only uses the module needs nothing new.

## Errors at render time

These templates rendered before and now fail. The message names the element,
the prop or style key and the value. In `nuxt dev`, the preview also shows the
line in the template.

<!-- changeset: change-invalid-values-fail -->

### `title` or `language` in `definePdf` and on `PdfDocument`

A template that sets `title` or `language` both in `definePdf` and on
`PdfDocument` fails with `PDF_TREE_INVALID`:

```text
The document title is set twice: in definePdf({ title }) and as "title" on <PdfDocument>. Set it in one place.
```

Before, the `definePdf` value replaced the `PdfDocument` prop without a
message. Keep the value in `definePdf`, so that `resolveMetadata(props)` can
read it before the render, and remove it from `PdfDocument`:

Before:

```text
definePdf({ title: props => `Invoice ${props.number}` })
<PdfDocument :title="`Invoice ${number}`">…</PdfDocument>
```

After:

```text
definePdf({ title: props => `Invoice ${props.number}` })
<PdfDocument>…</PdfDocument>
```

<!-- changeset: change-fonts -->

### A font weight without a registered face

A `fontWeight` that the family has no face for fails with `PDF_LAYOUT_ERROR`,
as a missing style already did:

```text
<PdfText> at pdfs/letter.vue:8:5 asks for Inter in fontStyle normal, fontWeight 700, but Inter has no normal face of weight 700 (registered: normal 400). Register the normal 700 face of Inter in `pdf.fonts`, or use a registered weight.
```

Before, the closest registered weight painted the text, so `bold` with only a
regular face printed regular text. Rich text `strong`, headings and table
header cells ask for 700. Register the face, or use a weight the message
lists. A variable font paints any weight inside its `wght` axis from one
registration.

<!-- changeset: change-fonts -->

### No hidden Helvetica for missing characters

A text uses only the fonts that `fontFamily` names. Before, a character that
the registered font lacked was painted in Helvetica. Now it shows as that
font's empty box (`.notdef`) and gives the layout warning `PDF_GLYPH_MISSING`;
a PDF/A or PDF/UA render fails. Register a font that contains the characters,
or set them in a nested text with their own `fontFamily`.

A space, a tab, a bidi control character and other characters that draw
nothing paint no glyph when the font lacks them. They no longer fail a PDF/A
render, and bidi controls no longer show as stray marks such as ".". Such a
space keeps its width of 0.278 em.

<!-- changeset: change-invalid-values-fail -->

### Negative sizes and values outside their range

A negative size, padding, border width or radius, `fontSize` or `lineHeight`,
and an `opacity` outside 0 to 1 fail with `PDF_TREE_INVALID`:

```text
<PdfView> :style value -4 for "paddingTop" is invalid: expected a value of 0 or more.
```

Margins, insets, `letterSpacing` and transforms can still be negative. Where a
negative size or padding moved an element, use 0 and a negative margin.

Before:

```text
<PdfView :style="{ paddingTop: -4 }">…</PdfView>
```

After:

```vue
<PdfView :style="{ marginTop: -4 }"><PdfText>Moved up by 4 pt</PdfText></PdfView>
```

The same check covers document metadata that is not a string, a `bookmark`
that is not a title or `{ title, expanded, contents }`, `widows`, `orphans` or
`maxLines` that are not positive whole numbers, and SVG colors that the
engine cannot read. Correct each value that the message names.

### Style values that the engine cannot read

A `:style` or `v-bind()` value that rendered wrong before now fails with
`PDF_TREE_INVALID`: an unsupported unit such as `em`, a misspelled color or
keyword, a color the engine cannot read such as `'currentColor'`, a keyword in
upper case such as `'Center'`, a form field color with alpha (a field draws
its colors without alpha), and `false`.

```text
<PdfText> :style value "1.2em" for "fontSize" is invalid: expected a number of points, a length such as 12pt, or a percentage.
```

Before:

```text
<PdfText :style="{ fontSize: '1.2em' }">Larger</PdfText>
```

After:

```vue
<PdfText :style="{ fontSize: 12 }">Larger</PdfText>
```

A value that rendered correctly still passes. See
[Style object values]($docs.styles#style-object-values).

<!-- changeset: change-pagination -->

### `break` where it cannot start a page

A `break` inside a row, a table row or cell, a `fixed` node or a node with
`wrap={false}` was ignored. It now fails with `PDF_TREE_INVALID`:

```text
<PdfText> cannot have "break" inside <PdfView>, whose flexDirection is "row": its children sit side by side, so a break cannot end the page for one of them. Put "break" on <PdfView> instead.
```

Before:

```text
<PdfView :style="{ flexDirection: 'row' }">
  <PdfText break>Part 2</PdfText>
</PdfView>
```

After:

```vue
<PdfView break :style="{ flexDirection: 'row' }">
  <PdfText>Part 2</PdfText>
</PdfView>
```

Put `break` on the row or `PdfTableRow`, remove `wrap={false}` from the
ancestor, or remove `break`.

<!-- changeset: change-invalid-values-fail -->

### `textTransform: 'upperfirst'`

A style object took `textTransform: 'upperfirst'`, which raised only the first
letter of the text. It is not CSS, and the `PdfStyle` type did not include it.
It now fails with `PDF_TREE_INVALID`:

```text
<PdfText> :style value "upperfirst" for "textTransform" is invalid: expected one of none, capitalize, lowercase, uppercase. "upperfirst" is not CSS; "capitalize" sets the first letter of every word in upper case, so to raise only the first letter of the text, write it in upper case.
```

Use `textTransform: 'capitalize'` to raise the first letter of every word, or
write the first letter of the text in upper case.

<!-- changeset: change-link-schemes -->

### Link targets other than web, mail and phone

`PdfLink` wrote any `href` into the PDF, also a relative path or a
`javascript:`, `file:` or `data:` URL. It now accepts `#id` and absolute
`http:`, `https:`, `mailto:` and `tel:` URLs, and any other value fails with
`PDF_TREE_INVALID`:

```text
<PdfLink> "href" "docs/terms" is not a link a PDF may open. Use an absolute URL with http:, https:, mailto: or tel:, or "#id" for an element of the document.
```

Write a relative link as an absolute URL. Remove a link with another scheme,
or print its target as text.

<!-- changeset: change-invalid-values-fail -->

### Content inside a leaf primitive

Text or an element inside `PdfImage`, an SVG shape, `PdfStop` or a page token
was dropped. It now fails with `PDF_TREE_INVALID`:

```text
<PdfImage> cannot contain text.
```

Before:

```text
<PdfImage src="logo.png">Logo</PdfImage>
```

After:

```vue
<PdfImage src="logo.png" alt="Logo" />
```

Remove the content, or put it next to the element.

### Page tokens outside a text

A page token directly in `PdfLink` or `PdfView` fails with
`PDF_TREE_INVALID`:

```text
Invalid PDF nesting: <PdfLink> cannot contain <PdfPageNumber>. Wrap it in <PdfText>. Keep that <PdfLink> outside any other text: <PdfLink><PdfText>… <PdfPageNumber /></PdfText></PdfLink>.
```

Before:

```text
<PdfLink href="#contents"><PdfPageNumber /></PdfLink>
```

After:

```vue
<PdfLink href="#contents"><PdfText>Page <PdfPageNumber /></PdfText></PdfLink>
```

<!-- changeset: change-one-render-path -->

### Values that are not plain data

A `ref` or another class instance inside a style or prop fails with
`PDF_TREE_INVALID`:

```text
The "style" prop on <PdfText> must be plain data: it contains a class instance.
```

Before:

```text
const color = ref('#a00')
const warning = { color }
```

After:

```vue
<script setup lang="ts">
const color = ref('#a00')
const warning = computed(() => ({ color: color.value }))
</script>

<template>
  <PdfText :style="warning">Overdue</PdfText>
</template>
```

### Images that are not in `pdfs/assets`

A `PdfImage` whose source the module did not admit fails with
`PDF_ASSET_INVALID`:

```text
The local PDF image "logo.png" was not found under pdfs/assets. Add the file or fix the path.
```

Add the file under `pdfs/assets`, or correct the path. See
[Images and fonts]($docs.images-and-fonts).

### Fixed content that leaves no room

Fixed content that leaves no room for the rest of the page fails at once with
`PDF_LAYOUT_ERROR`. Before, the render ran until `timeoutMs`. Make the fixed
content smaller, or move part of it into the flow.

<!-- changeset: change-pagination -->

### A fixed node between flow content

A `fixed` node that stands between flow content, directly on a `PdfPage` or
in a view, fails with `PDF_LAYOUT_ERROR`, also in a document of one page:

```text
A fixed <PdfText> at pdfs/invoice.vue:24:5 is between the flow content. A fixed node repeats on every page, so on a page that ends before it, the content of that page would be squeezed to make room for it. Put fixed nodes before the flow (a header) or after it (a footer written last), or give the node position: absolute.
```

In a view, the message names the view too ("is between the flow content of a
`<PdfView>` at …"). Before, a page that ended before the node squeezed its
content to make room for it, and lines overlapped. Move the node before the
flow of its page or view for a header, or after it for a footer. An absolute
`fixed` node, a `fixed` cell of a row, and a node inside a `fixed` or
`:wrap="false"` view can stay where they are.

<!-- changeset: change-pagination -->

### `flexWrap` on a page or a tall view

`flexWrap` on a `PdfPage` that breaks across pages and lays its content
out in a column (no `flexDirection: 'row'`) fails with `PDF_TREE_INVALID`:

```text
flexWrap "wrap" on <PdfPage> is not supported: a page puts the content that passes its end on the next page, not in another column. Remove flexWrap, or give the content a <PdfView> with columnCount for text in columns, or a <PdfView> with flexDirection "row" and flexWrap for a grid.
```

Before, content that passed the page end went into a second column first,
and lines were lost. Remove `flexWrap` from the page. For text in columns,
put it in a `PdfView` with `columnCount`. For a grid of cards, use a
`PdfView` with `flexDirection: 'row'` and `flexWrap`. A page with
`wrap={false}` can keep `flexWrap`.

A view with `flexWrap` and a `height` or `maxHeight` higher than a page
fails with `PDF_LAYOUT_ERROR`. Before, it broke across pages, and each page
wrapped its part of the children into other lines. Give the view a height
that fits on a page, or remove the height so it breaks as a column.

<!-- changeset: change-lengths -->

### Percentage heights in a parent without a height

A percentage `height`, `minHeight` or `maxHeight` fails with
`PDF_TREE_INVALID` when the parent has no height known before layout:

```text
<PdfView> has minHeight "90%", but its parent <PdfView> has no height known before layout: a percentage height is a share of the parent's height inside its paddings, which needs a height in points (or a percentage of a parent with one) and paddings and borders in points. Give the parent a height, or give the minHeight in points.
```

Before, such a percentage took the height of an ancestor further up, or of
the box the layout measures before it breaks the pages. Give the parent a
`height`, or give the node its height in points. A child of a `PdfPage` with a
height, and an absolute node, keep working as before.

<!-- changeset: change-pagination -->

### A `fixed` item in a wrapping row

A `fixed` child of a row with `flexWrap` fails with `PDF_LAYOUT_ERROR` when
the row breaks across pages:

```text
A fixed <PdfView> is an item of a <PdfView> with flexWrap "wrap" that breaks across pages. Repeated on the next page, it would wrap the other items into other lines. Put the fixed node before the row, in a <PdfView> that holds both, or remove its fixed prop.
```

Before, the item repeated on the next page as a line of its own, which the
row could not lay out again. Put the `fixed` node before the row, inside a
`PdfView` that holds both, so it repeats above the rest of the row. A row that
fits on one page keeps working as before.

## Changes without an error

These changes keep the template valid but can move content. Compare each
document in the preview after the upgrade.

<!-- changeset: change-lengths -->

### `px` lengths

A `px` length is `n × 72 / dpi` points, no longer rounded to whole points, in
styles and in the page size. On a page with `dpi: 96`, `'1px'` is 0.75 pt
instead of 1 pt, and a `'0.5px'` border at the default 72 dpi is 0.5 pt instead
of 1 pt. Where a size must stay a whole number of points, write it in points.

<!-- changeset: change-line-breaking -->

### Line breaks

Line breaks can move: text that is not justified keeps its natural spacing.

- Before, the layout put a little more text on a line than fit and then
  pressed the letters and spaces together. This applied to left, right and
  centered text, and to the last line of justified text. In a monospace font,
  a line could end past its box.
- Now a line holds only the words that fit at their natural width. A paragraph
  can get one more line, and a document can get one more page.
- Justified text stretches its spaces and never presses them together.
- A word wider than its box, such as a long number or a word with no
  hyphenation point, keeps its width and continues past the right edge of the
  box. Make the box wider, or put a space, a soft hyphen (`&shy;`) or a
  zero-width space (`&#8203;`) in the word.

Check the page count and the page breaks of documents with long paragraphs
or narrow table cells.

### Ragged line breaks

Left, right and centered text now ends its lines more evenly and splits
fewer words.

- Before, a hyphen was often the only allowed break, so a narrow ragged
  paragraph could get a hyphen on every third line.
- Now a line may end short, and a word splits only when that avoids a much
  shorter line. A paragraph can get one more line.
- Justified text keeps its breaks.

Check the page breaks of documents with long paragraphs in narrow columns.

### Break points

Lines now break where the Unicode line breaking rules allow, not only at
spaces. See [Where lines break]($docs.images-and-fonts#where-lines-break).

- Chinese and Japanese text without spaces wraps between characters. Before,
  it made one line that continued past its box.
- A line can break after a hyphen, a slash or an en dash, as in `e-mail` or
  `and/or`. Text in narrow boxes and table cells can get other line breaks.
- A line no longer breaks at a space before `!`, `?`, `:` or `;`.
- A zero-width space (U+200B) is a break point. A line or paragraph separator
  (U+2028, U+2029) ends the line; before, it was removed when the font lacked
  it.

Check the line and page breaks of documents with narrow boxes. To keep a
hyphenated word whole, put a word joiner (`&#8288;`) after its hyphen.

<!-- changeset: change-hyphenation-by-language -->

### Hyphenation

Words now split only at a soft hyphen (`&shy;`) in the text by default.
Before, every text hyphenated with American English patterns.

- A long word without a soft hyphen moves to the next line, or continues past
  the right edge of its box when it is wider than the box.
- The inherited style key `hyphens: 'auto'` splits words by the patterns of
  the document `language`. `language` only picks the patterns: with
  `language="de"` or `language="de-AT"`, German words split at German
  hyphenation points; `en-GB` uses British English patterns.
- A language without patterns, such as `tlh`, gives the layout warning
  `PDF_HYPHENATION_UNAVAILABLE` when a text has `hyphens: 'auto'`.

To keep automatic hyphenation, set `language` on `PdfDocument` or in
`definePdf`, and `hyphens: 'auto'` on the page:

```vue
<PdfDocument language="en">
  <PdfPage :style="{ hyphens: 'auto' }">
    <PdfText>Long words split by American English rules.</PdfText>
  </PdfPage>
</PdfDocument>
```

Then check the line and page breaks of documents with long words or narrow
columns. Set `hyphens: 'manual'` on a label that must stay whole.

<!-- changeset: change-line-height -->

### Line height

A unitless `lineHeight` is now a factor of each text's own font size, as in
CSS.

- Before, the factor became points where it was set: times that element's
  own `fontSize`, or times 18 when it had none. Its children inherited those
  points. A `lineHeight: 1.4` on a `PdfPage` without a `fontSize` gave 10 pt
  body text 25.2 pt lines, and a larger heading inside got too little space.
- Now each text multiplies the factor by its own font size: 14 pt lines for
  10 pt text, 28 pt lines for a 20 pt heading.
- A length (`'14pt'`) or a percentage (`'140%'`) still sets points where it
  is written, and children inherit those points. A percentage is now taken
  of the element's font size, its own or else the inherited one. Before, an
  element without its own `fontSize` took it of 18.

Text under an ancestor with a unitless `lineHeight` can get tighter or looser
lines, so pages can break differently. To keep a fixed line height, write it
in points or set it on the text itself.

<!-- changeset: change-line-height -->

### Text position in its line

A line height now puts half of its extra space above the glyphs and half
below, as in CSS. The extra space is the line height minus the font's glyph
height (ascent to descent).

- Before, all of it was below the glyphs. A 10 pt Helvetica text with
  `lineHeight: 2` now draws its glyphs 4.5 pt lower in each line, so the
  space above the first line and below the last one are equal.
- A line height below the glyph height moves the glyphs up: with
  `lineHeight: 1` they reach 0.5 pt above the line. Before, a line height
  below the font's ascent drew a CJK or Arabic text below its line.
- The background of a nested `PdfText` covers its glyph height, not the
  whole line.
- Line heights, line breaks and page breaks do not change. Text without a
  `lineHeight` does not move unless its font has a line gap.

Check the position of text in boxes with a set height, such as labels and
table cells with a `lineHeight`. Add a top padding or margin where the text
should sit lower.

### Page breaks

- A `break` inside a view that fits on the page now starts a new page. Before,
  it was ignored at that depth. Remove the `break` where you relied on that.
- A `break` on the first element of a page no longer adds an empty page before
  it.
- A view whose first page would hold only its `fixed` children, such as a
  repeated header alone at the page bottom, starts on the next page.
- A text that the `orphans` rule moves to the next page keeps its top margin,
  like every other node that moves whole. A node inside a view whose bottom
  margin does not fit on the page moves to the next page, as on the page
  itself. A wrapper view no longer changes where a node starts.
- Text in a box with a top padding or border, such as a table cell, no longer
  ends below the page edge: its last line moves to the next page.
- A text whose first lines are higher than the page no longer moves from page
  to page until the time limit: it keeps at least one line on each page.

### Tables

- A row that splits keeps every cell in its column on both pages, a cell whose
  lines fit stays on its page, and a header no longer ends a page alone.
- Share columns no longer move by the padding of a cell or by a span. A row
  with fewer cells than columns keeps the remaining columns empty at their
  width.
- An image in a row that splits is drawn once: it moves to the next page, or
  stays on its page when it is higher than the page.

### Text, bookmarks and output

- Right-aligned and centered text in a box narrower than its container sits on
  its edge or center. Before, it could be up to one space off.
- An absolute text, image or SVG without a width in a row gets the same size
  as in a column. Before, it could get no size.
- A node that splits across pages has one outline entry, on the page where it
  starts.
- A template that changes state after it rendered, such as with a timer or a
  late promise, no longer changes the PDF.
- An image that appears on several pages, such as a logo in a `fixed` header,
  is embedded once per document, so the file is smaller.
- Two renders of the same document write the same bytes.
- A text with `PdfPageNumber` or `PdfPageCount` uses its `lineHeight`. Before,
  it always had the font's normal line height. A footer with a `lineHeight`
  takes more room, and a footer placed with `bottom` moves up.
- Nuxt PDF writes the file with its own writer instead of PDFKit. The bytes of
  every document change; the pages look the same and give the same text. If a
  test compares rendered bytes with a stored file, store the file again.

<!-- changeset: change-one-color-rule -->

### Colors

A color's alpha now multiplies `opacity`, as in CSS. A background of
`rgba(0, 0, 0, 0.5)` with `opacity: 0.5` paints at 25 %; before, it took the
lower of the two, 50 %. A text color with alpha is no longer replaced by the
text's `opacity`. Such a background or text paints lighter: raise the alpha or
the opacity to keep the old look.

An `hsl()` color converts its hue, saturation and lightness as written;
before, they were rounded to whole numbers first. So `hsl(0, 100%, 50.4%)`
paints `#FF0202`, where it painted `#FF0000`. A channel that falls exactly half
way between two whole values now rounds up, so `hsl(350, 60%, 75%)` paints
`#E699A6`, one step redder than before.

An SVG `transform` written in another case, such as `Translate(10)`, now fails
with `PDF_TREE_INVALID`. Before, the shape was drawn without the transform.
Write the operation in lower case.

<!-- changeset: change-layout-warning-union -->

### Layout warnings in diagnostics

`diagnostics.layoutWarnings` can now hold more than one kind of warning, not
only `PDF_UNBREAKABLE_NODE_OVERFLOW`; the [render result]($docs.registry#the-render-result)
lists every code and its fields. `PdfLayoutWarning` is a union of them, so
TypeScript rejects code that reads `nodeHeight` or `availableHeight` without
checking `warning.code` first. Check `warning.code` before reading the other
fields.

### Error messages

Update code that matches error text:

- The error for page numbers that do not settle within `maxPasses` starts
  with "Page numbers did not stabilize".
- Compile error positions are file positions. Template compile errors moved
  from the line inside the `<template>` block to the line in the file.
- Tree validation messages name the element and its `id`, such as
  `<PdfText id="intro">`.
