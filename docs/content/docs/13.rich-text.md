`PdfRichText` prints formatted text that a CMS stores: the HTML of a rich text
editor such as TipTap, Lexical or Quill, Markdown, a document that comark
already parsed, or a rich text model that you map from the CMS's own JSON. It
renders headings, paragraphs, lists, quotes, code,
rules, links, images, tables, the marks bold, italic, underline, strikethrough and
code, superscript and subscript, and footnotes with the existing primitives. It is not an HTML compiler: it reads a fixed set of
editor tags and ignores CSS.

## Print editor HTML

Give the HTML to the `html` prop. Load it on the server and pass it to the
template as a prop:

```vue [pdfs/journal-post.vue]
<script setup lang="ts">
const props = defineProps<{ title: string, body: string }>()

definePdf<{ title: string, body: string }>({
  title: ({ title }) => title,
  language: 'en',
})
</script>

<template>
  <PdfDocument>
    <PdfPage size="A5" :style="{ padding: 40, fontFamily: 'Lora' }">
      <PdfText tag="h1" class="title">
        {{ props.title }}
      </PdfText>
      <PdfRichText :html="props.body" class="body" bookmarks />
    </PdfPage>
  </PdfDocument>
</template>

<style>
.title {
  font-size: 20pt;
  font-weight: 700;
  margin-bottom: 12pt;
}
.body {
  font-size: 10pt;
  line-height: 1.45;
}
</style>
```

`PdfRichText` takes exactly one of `html`, `content` and `comark`. With none or
more than one, the render fails with `PDF_TREE_INVALID`.

`parseRichTextHtml(html)` is the same HTML adapter as a function. It returns the
rich text model, so you can store it, test it, or change it before the render.
It is available in every template and component under `pdfs/` without an
import. In server code, import it from `#pdf` or `@lupinum/nuxt-pdf/server`.

## Print a model from CMS JSON

Many editors also save a JSON tree. Map it to the rich text model and give the
result to the `content` prop. This function maps the JSON of TipTap (and of
ProseMirror with the same node names):

```ts [server/utils/tiptap.ts]
import type { PdfRichBlock, PdfRichInline, PdfRichTextRun } from '@lupinum/nuxt-pdf'

export interface TipTapNode {
  type: string
  attrs?: Record<string, unknown>
  content?: TipTapNode[]
  marks?: Array<{ type: string, attrs?: Record<string, unknown> }>
  text?: string
}

const MARKS = ['bold', 'italic', 'underline', 'strike', 'code'] as const
const LEVELS = [1, 2, 3, 4, 5, 6] as const
const isMark = (type: string): type is typeof MARKS[number] => MARKS.some(mark => mark === type)

function inline(node: TipTapNode): PdfRichInline {
  if (node.type === 'hardBreak') return { type: 'break' }
  const run: PdfRichTextRun = { type: 'text', text: node.text ?? '' }
  for (const mark of node.marks ?? []) {
    if (isMark(mark.type)) run[mark.type] = true
    else if (mark.type === 'superscript') run.verticalAlign = 'super'
    else if (mark.type === 'subscript') run.verticalAlign = 'sub'
  }
  const link = node.marks?.find(mark => mark.type === 'link')
  return link ? { type: 'link', href: String(link.attrs?.href ?? ''), children: [run] } : run
}

function block(node: TipTapNode): PdfRichBlock[] {
  const children = node.content ?? []
  const start = node.attrs?.start
  switch (node.type) {
    case 'paragraph': return [{ type: 'paragraph', children: children.map(inline) }]
    case 'heading': return [{ type: 'heading', level: LEVELS.find(level => level === node.attrs?.level) ?? 2, children: children.map(inline) }]
    case 'bulletList':
    case 'orderedList': return [{ type: 'list', ordered: node.type === 'orderedList', ...(typeof start === 'number' ? { start } : {}), items: children.map(item => (item.content ?? []).flatMap(block)) }]
    case 'blockquote': return [{ type: 'quote', children: children.flatMap(block) }]
    case 'codeBlock': return [{ type: 'code', text: children.map(child => child.text ?? '').join('') }]
    case 'horizontalRule': return [{ type: 'rule' }]
    default: return []
  }
}

export const tiptapToRichText = (doc: TipTapNode): PdfRichBlock[] => (doc.content ?? []).flatMap(block)
```

The function drops node types that it does not know, such as images and
tables. A link with a target that is not allowed fails the render (see
[Links](#links)). Call `validateRichText(content)` before the render to find
such nodes: it returns a list of `PdfRichTextIssue` and never throws. It is
available where `parseRichTextHtml` is.

## Print Markdown

Markdown goes through [comark](https://comark.dev), an optional peer
dependency. Install it in your app:

```bash
pnpm add comark
```

comark parses only asynchronously, and a PDF template cannot await. So parse
the Markdown in the server route that loads the data, and give the model to the
`content` prop:

```ts [server/api/journal-post.get.ts]
import { parseRichTextMarkdown, pdf } from '#pdf'

export default defineEventHandler(async () => {
  // Load the post from your CMS here.
  const post = { title: 'Rain on a tin roof', markdown: '## Where to stand\n\nOut of the wind.' }
  const content = await parseRichTextMarkdown(post.markdown)
  const result = await pdf.journalPost.render({ title: post.title, content })
  return result.response()
})
```

```vue [pdfs/journal-post.vue (excerpt)]
<PdfRichText :content="props.content" class="body" bookmarks />
```

`parseRichTextMarkdown(markdown)` returns the rich text model. Import it from
`#pdf` or `@lupinum/nuxt-pdf/server`. It is not available in templates without
an import, because a template cannot await it. If you give its Promise to
`PdfRichText`, the render fails with `PDF_TREE_INVALID` and a message that says
where to await it.

comark runs in a render worker, the same worker pool that lays out PDFs. The
parse never blocks your server, and it has a time limit:
`pdf.limits.markdownTimeoutMs`, 5,000 ms by default, including the wait for a
free worker. Over the limit, the worker is stopped and the call fails with
`PDF_LIMIT_EXCEEDED`. The default only stops input that is slow on purpose or
by accident. To set a limit for one call, pass
`{ timeoutMs }` as the second argument (type `ParseRichTextMarkdownOptions`), a
whole number from 1 to 2,147,483,647 ms.

Call it on the Node server: in a server route, a server utility, or a Node
script with `@lupinum/nuxt-pdf/server`. A Nitro preset that bundles the server
into one file has no worker; there the call fails with `PDF_RENDER_ERROR`
instead of parsing on the main thread.

The same allowlist and [limits](#limits) apply as for HTML. Raw HTML
in the Markdown goes through the same rules: `script` and the other removed tags
go away with their content. Without `comark` installed, `parseRichTextMarkdown`
fails with `PDF_RENDER_ERROR` and a message that names the package and the
install command. Markdown over 250,000 characters fails with
`PDF_RICH_TEXT_INVALID` before it goes to the worker.

The tests run with comark 0.8.1 and 0.9.2. The peer range is `^0.8.1 || ^0.9.2`.

## Print a comark document

A project that already parses its content for the web with comark or Nuxt
Content has the parsed document. Give it to the `comark` prop as it is: the
object with `nodes`, or the node list.

```vue [pdfs/journal-post.vue (excerpt)]
<PdfRichText :comark="props.document" class="body" />
```

This path runs no parser and does not need the `comark` package. It checks the
shape first: each node must be a text or a `[tag, props, ...children]` array. A
wrong node fails with `PDF_RICH_TEXT_INVALID`, with a path such as
`comark.nodes[2][3]`. Then the same allowlist and limits apply as for HTML.

## Components

comark components, such as `::callout{tone="tip"}` in Markdown, become component
blocks in the model. Map their names to Vue components with the `components`
prop:

```vue [pdfs/journal-post.vue (excerpt)]
<script setup lang="ts">
import type { PdfRichBlock } from '@lupinum/nuxt-pdf'
import JournalCallout from './components/JournalCallout.vue'

const props = defineProps<{ content: PdfRichBlock[] }>()
const components = { callout: JournalCallout }
</script>

<template>
  <PdfRichText :content="props.content" :components="components" />
</template>
```

The component gets the props of the Markdown component and its content in the
default slot. A comark slot such as `#title` becomes a named slot. The component
uses the PDF primitives, like any component under `pdfs/`.

- A name matches exactly, as comark writes it. comark writes names in kebab
  case: `::JournalCallout` becomes `journal-callout`.
- A component without a mapping prints its content without a wrapper: first its
  named slots, then its default content.
- Props are plain JSON values. A bound prop such as `:count="3"` becomes the
  number `3`. `class`, `id` and `style` are dropped.
- A component gets only the props it declares. A prop name in the content
  matches a declared prop in camelCase, so `max-width="12"` reaches `maxWidth`.
  Other props, such as a typo, `onClick` or `ref`, are dropped without an error,
  so an editor's mistake does not stop the render, and each gives a
  [rich text warning](#dropped-input). The model keeps all props.
- Only a component at block level becomes a component block: at the top, in a
  quote, or in another component. A component inside a paragraph, a list item
  or a heading prints only its text: first the text of its named slots, then
  its default content.
- HTML input never makes components. An unknown HTML tag keeps its text.

## Accepted HTML

The adapter reads HTML in one pass and never throws on malformed markup: it
closes what is open and ignores an end tag without a start tag.

| HTML | Result |
| --- | --- |
| `p`, `div` and the other block tags, such as `section`, `dt`, `dd`, `figcaption` | A paragraph for loose text. |
| `h1` to `h6` | A heading of that level. Blocks inside a heading become its text. |
| `ul`, `ol` with `li` | A bulleted or numbered list. `start` on `ol` sets the first number. A list can hold lists. |
| `blockquote` | A quote. |
| `pre` | A code block. Spaces, tabs and line breaks stay. A `language-*` class on its `code` sets `language`. |
| `hr` | A horizontal rule. |
| `br` | A line break. |
| `strong`, `b` / `em`, `i` / `u` / `s`, `del`, `strike` / `code` | Bold / italic / underline / strikethrough / inline code. |
| `sup` / `sub` | Raised / lowered text, as the style `verticalAlign` places it, at 70 % of the text size (the `sup` and `sub` styles). A `sup` or `sub` inside another keeps the outer place. |
| `a` with `href` | A link. See [Links](#links). |
| A link to an item of a `section` with class `footnotes` | A footnote. See [Footnotes](#footnotes). |
| `span`, `font`, `mark` and other unknown tags | The text stays, without formatting. |
| `img` with `src` | An image. See [Images](#images). An `img` inside a paragraph ends the paragraph. |
| `figure` with one `img` and an optional `figcaption` | One image with a caption. A `figure` with other content prints its content. |
| `table` with `thead`, `tbody`, `tfoot`, `tr`, `th`, `td`, `caption`, `col` | A table. See [Tables](#tables). |
| `script`, `style`, `template`, `iframe`, `object`, `noscript`, `noembed`, `noframes`, `svg`, `math`, `textarea`, `xmp`, `head`, `title` | Removed with their content. |

The adapter ignores every attribute except `href` on `a`, `start` on `ol`,
`src`, `alt`, `width` and `height` on `img`, the `language-*` class of a
code block, and in a table `colspan`, `rowspan`, `align` and `text-align` on a
cell, and `span` and the width of a `col`.
Classes and other `style` declarations have no effect, and each gives a
[rich text warning](#dropped-input). It also ignores comments and
doctypes.

Whitespace follows the browser: a run of spaces, tabs and line breaks becomes
one space, and space at the start and end of a block goes away. `&nbsp;` stays.
The adapter decodes numeric character references and the named references that
editors write, such as `&amp;`, `&eacute;` and `&mdash;`.

An empty `<p></p>` is dropped, because a browser shows no line for it.
`<p><br></p>`, which editors write for an empty line, stays as an empty line.

## Dropped input

The adapter never stops the render for content it cannot print, but it does
not drop it without a word either. Each render lists in
`result.diagnostics.richTextWarnings` what `html` and `comark` input lost or
changed, and the development preview shows the list:

```ts
result.diagnostics.richTextWarnings
// [{ code: 'PDF_RICH_TEXT_ATTRIBUTE_DROPPED', name: 'style', count: 14,
//    message: 'Inline styles do not reach the PDF. Style the elements with the "styles" prop of PdfRichText.',
//    snippet: 'style="color: #c00"', source: { file: 'pdfs/journal-post.vue', line: 12, column: 5 } }]
```

| `code` | What happened |
| --- | --- |
| `PDF_RICH_TEXT_LINK_DROPPED` | A link prints as plain text: a target that is not an absolute `http:`, `https:`, `mailto:` or `tel:` URI (`name` is its scheme, such as `javascript:`, or `relative` or `#`), a link inside a link (`nested`), or a link around an image (`image`). |
| `PDF_RICH_TEXT_ATTRIBUTE_DROPPED` | An attribute that the adapter does not read, such as `style`, `class` or `title`. All `data-*` attributes count as `data-*` and all `aria-*` as `aria-*`. An `id` prints nothing and gives no warning. |
| `PDF_RICH_TEXT_TAG_DROPPED` | A tag removed with its content, such as `script` or `iframe`. |
| `PDF_RICH_TEXT_TAG_UNKNOWN` | A tag off the allowlist, such as `font` or `mark`: its text prints without its formatting. |
| `PDF_RICH_TEXT_VALUE_CHANGED` | A value cut or left out: an `alt` over 1,000 characters, an `img` without a usable `src`, an image `width` or `height` that is not a number of pixels, an `ol` `start` that is not a whole number, a `colspan` or `rowspan` that is not a whole number or runs past the table, or `col` widths that do not apply. |
| `PDF_RICH_TEXT_COMPONENT_DROPPED` | A component that prints its content without its Vue component: it has no entry in `components`, or it sits inside a paragraph, list item or heading. |
| `PDF_RICH_TEXT_PROP_DROPPED` | A prop that a component does not get: its Vue component does not declare it, it is Vue's own (`key`, `ref`), or its value is not plain JSON. `name` is `component.prop`. |

A render has one entry per `code` and `name`, with `count`, the number of times
the render met it in all its `PdfRichText` elements. So content with a
`data-*` attribute on every paragraph gives one entry. `message` names tags and
attributes only. In development, `snippet` shows the first occurrence as the
adapter read it (at most 80 characters) and `source` names the `PdfRichText`
in the template. In production both are absent, so the warnings contain no
content. A model given to `content` fails instead of dropping anything, and
`parseRichTextMarkdown` runs before the render, so its result has no warnings.

## Markdown and comark details

comark produces the same tags as HTML, so the table above applies. In addition:

| Markdown | Result |
| --- | --- |
| A fenced code block with a language | A code block with `language`. The code has no syntax colors. |
| An image, `![alt](src "title")` | An image with its alt text, the same as `img`. The title is ignored. |
| A table | A table with a header row and the alignment of its columns. See [Tables](#tables). |
| A task list | A list. The text of each item stays, the checkbox does not. |
| A footnote, `[^1]` with its definition `[^1]: The note.` | A footnote. See [Footnotes](#footnotes). |
| `H~2~O`, `m^2^` | Stays as written: comark has no syntax for subscript or superscript. Write `H<sub>2</sub>O` and `m<sup>2</sup>`. |
| Frontmatter, the `id` of a heading | Ignored. |
| An HTML comment | Ignored. |

comark decodes character references itself. A Markdown link with a relative path
or an `#id` keeps its text. comark does not read a `javascript:` link as a link,
so it prints as written (see [Links](#links)).

## Footnotes

A footnote from Markdown or from editor HTML becomes a
[`PdfFootnote`]($docs.primitives#pdffootnote): a raised number in the text,
and the note at the bottom of the page.

In Markdown, write a reference and its definition:

```text [Markdown]
Peat stores twice as much carbon as all forests.[^peat]

[^peat]: Source: the **peatland report**, page 12.
```

- A definition is one line. The next line starts a new paragraph.
- A note is one paragraph of text. A note that is a list or a heading, such
  as `[^1]: - one`, fails with `PDF_RICH_TEXT_INVALID`.
- A note can hold bold, italic, code and links.
- A reference used twice prints the same number twice and one note.
- A reference without a definition fails with `PDF_RICH_TEXT_INVALID`:
  without its note, the text would print a stray `^1`. A definition without a
  reference is dropped.
- A line that starts like a definition, such as `[^1]: x`, inside a fenced
  code block fails with `PDF_RICH_TEXT_INVALID`, and the message names the
  line: comark would take the line out of the code. Indent that code by four
  spaces instead of fencing it.

In HTML, the markup that Markdown renderers write works: a link to `#fn1`,
where `fn1` is the `id` of a list item in a `section` or `div` with class
`footnotes` at the top level. The link text, such as `[1]`, is not kept: the
mark prints the number. The list prints nothing else, and its back links are
dropped. A `sup` with class `footnote-ref` around a link to no note fails with
`PDF_RICH_TEXT_INVALID`, and so does a note with two paragraphs, a list or
another block. A link inside a note is a link, also when it points
to another note: a note has no notes.

The `comark` prop runs no parser, so a document parsed with comark's footnotes
plugin keeps each note as its Markdown source, and `**bold**` prints with its
asterisks. Parse the Markdown with `parseRichTextMarkdown` to get the notes
parsed.

In the model, a footnote is an inline `PdfRichFootnote`. A later footnote with
only the `key` of an earlier one marks that note again:

```ts
const children: PdfRichInline[] = [
  { type: 'text', text: 'Peat' },
  { type: 'footnote', key: 'peat', children: [{ type: 'text', text: 'Source: the peatland report.' }] },
  { type: 'text', text: ' and bogs' },
  { type: 'footnote', key: 'peat' },
]
```

## Tables

A table in HTML or Markdown becomes a [`PdfTable`]($docs.tables): the header
row repeats at the top of every page of the table, and the cells keep their
spans and alignment.

```text [Markdown]
| Site  | Carbon (t/ha) |
| :---- | ------------: |
| North |           420 |
| South |           380 |
```

- The header is the one row of `thead`. Without `thead`, a first row of `th`
  cells only is the header, as editors such as TipTap write it. Markdown
  tables always have a header.
- A `th` in a body row is the header of its row.
- `tfoot` rows print after the body rows, once.
- `colspan` and `rowspan` work as in a browser. A `rowspan` past the last row,
  or a `colspan` into a cell that a `rowspan` from above takes, is cut to the
  space that is free.
- `text-align` (which Markdown writes for `:---:`) or `align` on a cell sets
  `left`, `center` or `right`.
- Every column is `'auto'`: as wide as its content on one line, and narrower
  together when the table has less room, so the text wraps inside its cells.
  The widths of `col` elements set the proportions of the columns, when every
  column has one, all in `px`, `pt` or plain numbers, or all in `%`: the table then fills its
  room, so widths written for a screen never make it wider than the page.
- A `caption` prints above the table in the `caption` style and stays on the
  page of the table.
- Text or elements outside the cells print before the table, as a browser
  shows them.

A cell holds text: marks, links, line breaks, footnotes and paragraphs. These
fail with `PDF_RICH_TEXT_INVALID`, so a table does not change without a word:

| Input | Why it fails |
| --- | --- |
| A list, an image, a code block, a quote, a heading, a table, a rule or a component in a cell | A cell holds text and paragraphs only. |
| A `thead` with more than one row | The header is one row that repeats on every page. |
| A `rowspan` in the header | The same. |
| A footnote in a header cell | The header repeats on every page, and so would its note. |

In the model, a table is a `PdfRichTable`. `columns` takes the widths as
`PdfTable` does; leave it out for `'auto'` columns:

```ts
const table: PdfRichBlock = {
  type: 'table',
  header: [{ children: [{ type: 'paragraph', children: [{ type: 'text', text: 'Site' }] }] }],
  rows: [[{ children: [{ type: 'paragraph', children: [{ type: 'text', text: 'North' }] }] }]],
}
```

## Links

A link keeps its target only for an absolute `http:`, `https:`, `mailto:` or
`tel:` URL. The adapter drops other links and keeps their text: a relative path,
`#id`, `javascript:`, `data:` and other schemes, and gives a
[rich text warning](#dropped-input) for each. In a model given to `content`,
such a link fails the render with `PDF_RICH_TEXT_INVALID`.

## Images

An image block prints with `PdfImage` and follows the same source rules:

- A path such as `photos/heron.jpg` loads a PNG or JPEG file from
  `pdfs/assets`. See [Images and fonts]($docs.images-and-fonts).
- An `https:` URL loads only when it matches `pdf.remote.allow`. See
  [Remote images]($docs.remote-images).
- Every other source is refused: `data:`, `file:` and other schemes, absolute
  paths, `..` in a path, and a host that is not on the allowlist. Nothing else
  reaches the disk or the network.

```vue [pdfs/journal-post.vue (excerpt)]
<PdfRichText :html="props.body" />
```

```text [Editor HTML]
<figure>
  <img src="photos/meadow.jpg" alt="The meadow at dawn" width="240">
  <figcaption>The meadow in April.</figcaption>
</figure>
```

Without `width` and `height`, an image fills the width of its column and keeps
its proportions. With `width` or `height`, it keeps that size in points and its
proportions. An image is never wider than its column: a larger `width` scales
it down. `width` and `height` are read only as plain numbers, such as `240` or
`120.5`. A unit, such as `240px`, CSS and `style` are ignored.

## Broken images

A rich text image whose source the asset rules refuse fails the render. The
error has the code of the asset error, and its message starts with the image
path, such as `<PdfRichText> image content[2]: …`.

An editor can save a link that does not resolve. When the PDF must render
anyway, set `brokenImages="placeholder"`:

```vue [pdfs/journal-post.vue (excerpt)]
<PdfRichText :html="props.body" broken-images="placeholder" />
```

The image then prints as a gray box with its alt text, and
`result.diagnostics.imageWarnings` gets one `PdfImageWarning`:

```ts
result.diagnostics.imageWarnings
// [{ code: 'PDF_RICH_TEXT_IMAGE_REPLACED', reason: 'PDF_ASSET_INVALID', path: 'content[2]' }]
```

`reason` is `PDF_ASSET_BLOCKED` for a source that the rules refuse or a remote
request that fails, and `PDF_ASSET_INVALID` for a file that is missing or is not
a valid image. `path` names the image in the rich text model; for `html` and
`comark`, it is the path in the model that the input maps to. The warning does
not contain the source. In development, `source` names the `PdfRichText` in the
template, and the [preview]($docs.errors-and-debugging) lists the warnings.
To find the cause, remove `brokenImages="placeholder"` and read the error.

A limit fails the render in both modes with `PDF_LIMIT_EXCEEDED`: an image over
`pdf.limits.maxTotalImageBytes` or `maxTotalImagePixels`, too many remote
requests, or the render timeout. Limits protect the server, so a placeholder
does not replace them.

## Styling

The style of `PdfRichText` itself applies to all of its text. A class works
like on any component. The defaults follow the body font size `s`: the size the
rich text inherits from the page or a parent, or its own `fontSize`. Heading
and caption sizes are percentages of it, and margins, paddings and the list
indent are `em` lengths, so they follow `s` without a size on `PdfRichText`.
Without a font size anywhere, `s` is 18 pt, the engine's text size. A heading
stays on the page of the first lines of what follows (`keepWithNext`). The
broken-image box is at least 36 pt high, a value in points that does not follow
the inherited size: it uses 3 × the `fontSize` of `PdfRichText` instead when it
has one in points. `styles: { imagePlaceholder: { minHeight } }` replaces it.

Change single elements with the `styles` prop. Each style merges over the
default of its element:

```vue [pdfs/journal-post.vue (excerpt)]
<PdfRichText
  :html="props.body"
  :styles="{ h2: { fontFamily: 'Inter', fontWeight: 700 }, link: { color: '#2f6f62' } }"
/>
```

| Key | Element | Default (at font size `s`) |
| --- | --- | --- |
| `p` | Paragraph | `marginBottom: '0.6em'` |
| `h1` to `h6` | Heading | Bold, `fontSize` `'200%'`, `'160%'`, `'135%'`, `'115%'`, `'100%'` and `'90%'`, `lineHeight` 1.25, `marginTop` 1 em of the body (none on the first block) and `marginBottom` 0.6 em of the body. In em of the heading these are 0.5 and 0.3 (h1), 0.625 and 0.375 (h2), 0.7407 and 0.4444 (h3), 0.8696 and 0.5217 (h4), 1 and 0.6 (h5), 1.1111 and 0.6667 (h6). |
| `list` | A whole list | `marginBottom: '0.6em'` |
| `listItem` | One item, a row of marker and text | `marginBottom: '0.25em'` |
| `marker` | The number or bullet | Right-aligned, `paddingRight: '0.4em'`, in a column 0.6 em wide per character of the widest number (at least two) plus 0.4 em |
| `quote` | Quote | 2 pt gray left border, `paddingLeft: '0.8em'`, `marginBottom: '0.6em'` |
| `code` | Inline code | Light gray background |
| `codeBlock` | Code block | Light gray background, `padding: '0.5em'`, `marginBottom: '0.6em'` |
| `link` | Link | Blue, underlined |
| `strong` | Bold text | `fontWeight: 'bold'` |
| `em` | Italic text | `fontStyle: 'italic'` |
| `sup` | Raised text, from `<sup>` | `fontSize: '70%'` |
| `sub` | Lowered text, from `<sub>` | `fontSize: '70%'` |
| `rule` | Horizontal rule | 0.75 pt gray top border, `marginTop: '0.3em'`, `marginBottom: '0.9em'` |
| `image` | An image, or the figure around an image with a caption | `marginBottom: '0.6em'` |
| `caption` | The caption of an image | `fontSize: '85%'`, gray, `marginTop` 0.3 em of the body (0.3529 em of the caption) |
| `imagePlaceholder` | The box of a [broken image](#broken-images) | 0.75 pt gray border, light gray background, `padding: '0.5em'`, `minHeight` 36 pt, which `minHeight` replaces (see above) |
| `table` | A table | `marginBottom: '0.6em'` |
| `tableHeader` | The header row | 1 pt gray bottom border |
| `tableRow` | A body row | 0.5 pt light gray bottom border |
| `tableCell` | Every cell | `paddingTop` and `paddingBottom` `'0.3em'`, `paddingLeft` and `paddingRight` `'0.5em'` |
| `tableHeaderCell` | A header cell, also the header of a row; over `tableCell` | `fontWeight: 'bold'` |

A `fontSize` you set for a heading or the caption in `styles` also scales its
default margins, because they are `em` of its own size. Set `marginTop` and
`marginBottom` too to keep other values.

The first block loses its top margin and the last block its bottom margin, so
`PdfRichText` adds no space at its edges. An unknown key fails the render with
`PDF_TREE_INVALID`.

`styles: { image: { float: 'top' } }` moves every image and figure of the
content to the top of its column or page, as a [float]($docs.styles#floats);
`'bottom'` moves them to the bottom. The content cannot float a single image:
HTML `style` and `class` attributes are not read. An image inside a list item
cannot float, because the item's content stands beside its marker; the render
fails with `PDF_TREE_INVALID` and names the image's content path.

Bold and italic text needs the bold and italic faces of the font family. If a
face is not registered, the render fails with `PDF_LAYOUT_ERROR`. Register the
face, or set `strong` or `em` to a style that the family has. Code uses the text
font with a background. For a monospace font, register it and set it on `code`
and `codeBlock` with `fontFamily`.

A bulleted list uses `•`. A bulleted list inside another list uses `-`.

## Page breaks, bookmarks and tagged PDF

Paragraphs, list items, quotes and code blocks break across pages. A table
breaks between its rows, and a row that does not fit splits at the page end;
the rows that a `rowspan` covers stay together. An image
does not break: when it does not fit below the content before it, it moves to
the next page. An image without a size is never taller than the page. A
heading
moves to the next page when less than about two lines of the next block fit
below it. This works for headings that follow other content inside the same
`PdfRichText`.

With `bookmarks`, each heading becomes an outline entry in the PDF reader. The
entries are flat: a heading level does not nest them.

With `conformance: 'PDF/UA-1'`, headings become `H1` to `H6`, paragraphs `P`,
lists `L` with `LI` and `LBody`, quotes `BlockQuote`, tables `Table` with
`TR`, `TH` and `TD` as [`PdfTable`]($docs.tables) writes them (a table
caption is the table's first kid, a `Caption`), links `Link` and images
`Figure` with the alt text as `Alt`, in reading order. An image with a caption
is one `Figure` that holds a `Caption`. A broken image prints its alt text as a
`P`. An image without alt text fails the render with `PDF_TREE_INVALID`, and the
message names its path, such as `<PdfRichText> image content[3] needs
alternative text`. Add the alt text in the editor. The marker is the first `P` of `LBody`. The heading levels of the
HTML must follow the levels of the document: a skipped level fails the render
with `PDF_TREE_INVALID`. See [Accessible PDF]($docs.accessible-pdf).

## Limits

Rich text comes from editors and users, so the input has fixed limits. Input
over a limit fails with `PDF_RICH_TEXT_INVALID` before the layout starts. The
Markdown parse time is the exception: it fails with `PDF_LIMIT_EXCEEDED`.

| Limit | Value |
| --- | --- |
| HTML length or total text | 1,000,000 characters |
| Markdown length | 250,000 characters, about a 100-page article |
| Elements or model nodes | 50,000 |
| Nesting depth | 32 |
| Images | 100 per `PdfRichText` |
| Image `src` | 4,096 characters |
| Image alt text | 1,000 characters |
| Image `width` and `height` | 10,000 points |
| Table columns | 64 per table |
| Markdown parse time | `pdf.limits.markdownTimeoutMs`, 5,000 ms by default |

In HTML and Markdown, a longer alt text is cut, and an image with a longer
`src`, or a `width` or `height` outside the range, loses that value: the image
is dropped, or prints without the size. In a model given to `content`, these
values fail with `PDF_RICH_TEXT_INVALID`. The image files themselves count
toward the image limits of the render (see
[Errors and limits]($docs.errors-and-limits)).

comark is much slower than the HTML parser on hostile input. So the Markdown
parse also has a time limit, `pdf.limits.markdownTimeoutMs`
(see [Print Markdown](#print-markdown)). It fails with `PDF_LIMIT_EXCEEDED`.
The length limit is lower than for HTML so that the default time limit, sized
for the longest honest input, stays short.

`PDF_RICH_TEXT_INVALID` carries `issues`, a list of `PdfRichTextIssue`. Each
issue has a `rule` (`PDF-RICH-NODE` for a wrong node, `PDF-RICH-LIMIT` for a
limit), a `path` such as `content[2].items[0][1].children[3].href`, and a
`message`. A message names the wrong field and value or the limit. It never
quotes the text of the article. The list stops after 20 issues.

### Not supported yet

- A link around an image. The image prints without the link.
- An image inside a heading or a code block. It is dropped.
- Syntax colors in code blocks.
- Components inside a paragraph, a list item or a heading.
- Lists, images and other blocks in a table cell, and a table header of more
  than one row.
- CSS and `style` attributes in the HTML, so no text color or size from the
  HTML, no alignment except in table cells, and no image size from CSS. Set
  them with `styles`.
- A footnote definition over more than one line.

A heading that is the first block of a `PdfRichText` does not take part in
the check that keeps a heading with the text after it.

## Model reference

The model is plain data that you can store and send as JSON. Import the types
from `@lupinum/nuxt-pdf`. `ParseRichTextMarkdownOptions` comes from
`@lupinum/nuxt-pdf/server`.

| Type | Shape |
| --- | --- |
| `PdfRichBlock` | One of the block types below. |
| `PdfRichParagraph` | `{ type: 'paragraph', children: PdfRichInline[] }` |
| `PdfRichHeading` | `{ type: 'heading', level: 1 \| 2 \| 3 \| 4 \| 5 \| 6, children: PdfRichInline[] }` |
| `PdfRichList` | `{ type: 'list', ordered: boolean, start?: number, items: PdfRichBlock[][] }`: each item is a list of blocks. |
| `PdfRichQuote` | `{ type: 'quote', children: PdfRichBlock[] }` |
| `PdfRichCode` | `{ type: 'code', text: string, language?: string }`: a code block. |
| `PdfRichComponent` | `{ type: 'component', name: string, props: Record<string, PdfRichJsonValue>, children: PdfRichBlock[], slots?: Record<string, PdfRichBlock[]> }`, see [Components](#components). |
| `PdfRichRule` | `{ type: 'rule' }` |
| `PdfRichImage` | `{ type: 'image', src: string, alt?: string, width?: number, height?: number, caption?: PdfRichInline[] }`, see [Images](#images). An empty `alt` is invalid; leave it out. |
| `PdfRichTable` | `{ type: 'table', columns?: PdfTableColumnWidth[], header?: PdfRichTableCell[], rows: PdfRichTableCell[][], caption?: PdfRichInline[] }`, see [Tables](#tables). `columns`, when set, has one width per column. A table has at least one cell. |
| `PdfRichTableCell` | `{ children: PdfRichParagraph[], colspan?: number, rowspan?: number, align?: 'left' \| 'center' \| 'right', header?: boolean }`: `colspan` and `rowspan` are whole numbers from 1; a header cell has no `rowspan` and no footnote; `header` makes a body cell the header of its row. |
| `PdfRichInline` | One of the inline types below. |
| `PdfRichTextRun` | `{ type: 'text', text: string, bold?, italic?, underline?, strike?, code?: boolean, verticalAlign?: 'super' \| 'sub' }`: `verticalAlign` raises or lowers the run in the `sup` or `sub` style, as `<sup>` and `<sub>` do. |
| `PdfRichLink` | `{ type: 'link', href: string, children: PdfRichInline[] }`: a link cannot hold a link. |
| `PdfRichBreak` | `{ type: 'break' }` |
| `PdfRichFootnote` | `{ type: 'footnote', key?: string, children?: PdfRichInline[] }`: with `children`, a note; with only `key`, a mark of the earlier note with that key. A key has 1 to 64 characters. Not inside a link or a note. See [Footnotes](#footnotes). |
| `PdfRichJsonValue` | A string, finite number, boolean, `null`, or an array or plain object of these. |
| `ParseRichTextMarkdownOptions` | `{ timeoutMs?: number }`: the options of one `parseRichTextMarkdown` call; `timeoutMs` replaces `pdf.limits.markdownTimeoutMs` for that call. |
| `PdfRichTextIssue` | `{ rule, path, message }`, see [Limits](#limits). |

A node with a field that its type does not have is invalid. A component name has
1 to 64 characters. A prop name starts with a letter or `_` and has letters,
digits, `_` and `-`. Props count toward the [limits](#limits). The
component types are `PdfRichTextProps`, `PdfRichTextStyles` and
`PdfRichTextStyleKey`. `PdfImageWarning` is the type of an entry of
`diagnostics.imageWarnings`, and `PdfRichTextWarning` (with
`PdfRichTextWarningCode`) of an entry of `diagnostics.richTextWarnings`.
