PDF/A-3b is the archival form of PDF that e-invoice standards build on. A
Factur-X invoice (in Germany: ZUGFeRD 2) is a PDF/A-3b document that carries
the invoice data as an embedded XML file, so a person reads the pages and
accounting software reads the XML.

Set `conformance="PDF/A-3b"` on `PdfDocument` for an archival document. Add
`PdfFacturX` for a hybrid invoice; it makes the document PDF/A-3b without
`conformance`. To write the invoice XML from invoice data, see
[E-invoices]($docs.e-invoices). This page explains PDF/A and how to embed XML
that your application writes. For an archival document that is also accessible, use
`'PDF/A-3a'`, the tagged PDF/A level. See [Accessible PDF]($docs.accessible-pdf).

## Register a font for every text

PDF/A requires that every painted letter comes from a font embedded in the
file. The standard PDF fonts (Helvetica, the default, Times, and Courier) are
not embedded, so a text that uses one of them fails the render.

1. Register a font in `pdf.fonts`. See
   [Register a local font]($docs.images-and-fonts).
2. Set `fontFamily` on every `PdfPage`, so every text inherits it:

```vue
<PdfDocument title="Archive copy" conformance="PDF/A-3b">
  <PdfPage size="A4" :style="{ fontFamily: 'Invoice Sans' }">
    <PdfText>Archive copy</PdfText>
  </PdfPage>
</PdfDocument>
```

A text without a registered family fails with `PDF_TREE_INVALID` and its
source position:

```text
PDF/A-3b requires embedded fonts, but <PdfText> uses the standard font "Helvetica", which is not embedded. Register a font in pdf.fonts (nuxt.config) and set fontFamily on the text, its page or a parent view.
```

Two cases need more than the page font:

- **SVG text does not inherit `fontFamily` from the page.** Set it in the
  style of each `PdfText` inside `PdfSvg`:
  `<PdfText :x="0" :y="10" :style="{ fontFamily: 'Invoice Sans' }">`.
- **A character that the registered font does not contain**, such as a tab or
  an emoji, is painted in Helvetica. The message names the characters and the
  font. Replace them (a tab with spaces, for example) before the render, or
  register a font that contains them.

## Add the XML invoice

Use `xml` when your application or another system writes the XML, for
example for the `EXTENDED` profile. To let Nuxt PDF write the XML from invoice
data, use `invoice` instead; see [E-invoices]($docs.e-invoices).

Put one `PdfFacturX` inside `PdfDocument`, next to the pages. Pass the XML
content and the Factur-X profile that the XML follows:

```vue [pdfs/invoice.vue]
<script setup lang="ts">
interface Props {
  invoice: { number: string, xml: string }
}

definePdf<Props>({
  title: props => `Invoice ${props.invoice.number}`,
  filename: props => `invoice-${props.invoice.number}.pdf`,
})

defineProps<Props>()
</script>

<template>
  <PdfDocument language="en">
    <PdfFacturX :xml="invoice.xml" profile="EN 16931" />
    <PdfPage size="A4" :style="{ fontFamily: 'Invoice Sans' }">
      <PdfText>Invoice {{ invoice.number }}</PdfText>
    </PdfPage>
  </PdfDocument>
</template>
```

Your application writes the XML. Nuxt PDF embeds it after two checks: the XML
is well-formed with a `CrossIndustryInvoice` root element, and it names the
profile you pass in the profile ID (BT-24, the
`GuidelineSpecifiedDocumentContextParameter` ID). A comment or a CDATA section
does not count as the profile ID. Nuxt PDF does not validate the XML against
the CII schema, and does not check the amounts or whether the XML matches the
printed pages. Validate the XML with a Factur-X or EN 16931
validator in your application tests; see
[Validate your invoices]($docs.e-invoices#validate-your-invoices).

Escape every data value before you put it into the XML.

### Profiles and file names

| `profile` | Profile ID that the XML must name | Embedded file name | Default `relationship` |
| --- | --- | --- | --- |
| `'MINIMUM'` | `urn:factur-x.eu:1p0:minimum` | `factur-x.xml` | `'Data'` |
| `'BASIC WL'` | `urn:factur-x.eu:1p0:basicwl` | `factur-x.xml` | `'Data'` |
| `'BASIC'` | `urn:cen.eu:en16931:2017#compliant#urn:factur-x.eu:1p0:basic` | `factur-x.xml` | `'Alternative'` |
| `'EN 16931'` | `urn:cen.eu:en16931:2017` | `factur-x.xml` | `'Alternative'` |
| `'EXTENDED'` | `urn:cen.eu:en16931:2017#conformant#urn:factur-x.eu:1p0:extended` | `factur-x.xml` | `'Alternative'` |
| `'XRECHNUNG'` | An ID that starts with `urn:cen.eu:en16931:2017#compliant#urn:xeinkauf.de:kosit:xrechnung_`, such as `…xrechnung_3.0` | `xrechnung.xml` | `'Alternative'` |

[Profiles]($docs.e-invoices#profiles) says what each profile holds and which
profiles count as e-invoices in Germany.

`relationship` sets how the XML relates to the pages (the PDF `AFRelationship`
key). Factur-X allows `'Data'`, `'Alternative'`, and `'Source'`. `MINIMUM`
and `BASIC WL` must use `'Data'`, because the pages hold more than the XML
(Factur-X 1.07.2, section 6.2.2). Keep the default unless your recipient asks
for another value.

The XML bytes count against
[`pdf.limits.maxTotalAttachmentBytes`]($docs.errors-and-limits), together with
the files of all `PdfAttachment` elements.

## What the render writes

For a document that claims PDF/A-3b or PDF/A-3a, the render:

- writes the file as PDF 1.7;
- writes an XMP metadata stream with the PDF/A identification (conformance B
  or A) and the title,
  author, subject, keywords, creator, and creation date of the document;
- adds an sRGB output intent, so the colors of the document have a defined
  meaning;
- gives every embedded file a MIME type (`application/octet-stream` when a
  `PdfAttachment` has no `type`);
- with `PdfFacturX`, embeds the XML with the Factur-X metadata (document type
  `INVOICE`, the file name, version `1.0`, and the profile).

A document without `conformance` and without `PdfFacturX` gets none of this
and keeps its bytes.

## Failures

Each of these fails the render with `PDF_TREE_INVALID`:

| Cause | Message | Inspect or change |
| --- | --- | --- |
| A text in a standard font | `PDF/A-3b requires embedded fonts, but <PdfText> uses the standard font "Helvetica", …` | Register a font and set `fontFamily` on the page. |
| SVG text in a standard font | `PDF/A-3b requires embedded fonts, but <PdfText> inside <PdfSvg> uses the standard font "Helvetica", …` | Set `fontFamily` in the style of the SVG text. |
| A character the font does not contain | `PDF/A-3b requires embedded fonts, but <PdfText> has characters that font "Invoice Sans" does not contain: U+0009. …` | Replace the named characters, or register a font that contains them. |
| `creationDate` is an Invalid Date or after the year 9999 | `<PdfDocument> requires "creationDate" to be a valid Date, …` | Pass a valid `Date` with a four-digit year. |
| `pdfVersion` other than `'1.7'` | `<PdfDocument> claims PDF/A-3b, which is written as PDF 1.7; remove "pdfVersion" or set it to "1.7".` | Remove `pdfVersion`. |
| A `PdfNote` | `<PdfNote> is not supported in a PDF/A document: …` | PDF/A requires a printed appearance for every note, which the engine does not write. Print the note as `PdfText`. |
| Two PDF/A levels in one list | `<PdfDocument> requires "conformance" to be "PDF/A-3b", "PDF/A-3a" or "PDF/UA-1", or a list of them with at most one PDF/A level.` | Keep one PDF/A level. |
| `profile` missing or not one of the six | `<PdfFacturX> requires "profile" to be "MINIMUM", "BASIC WL", "BASIC", "EN 16931", "EXTENDED" or "XRECHNUNG".` | Pass one of the six profiles. |
| The XML is not well-formed | `<PdfFacturX> "xml" is not well-formed XML: the closing tag </ram:ID> does not match <ram:Name> (line 12).` | Fix the XML at the named line. A DOCTYPE is rejected too. |
| The XML is not a CII invoice | `<PdfFacturX> "xml" has the root element <Invoice>; …` | Embed a CII file with the root element `rsm:CrossIndustryInvoice`. |
| The XML bytes are not UTF-8 | `<PdfFacturX> "xml" is not UTF-8 text; Factur-X requires a UTF-8 XML file.` | Write the XML as UTF-8. |
| The XML names no profile | `<PdfFacturX> "xml" does not name a profile: …` | Add the profile ID (BT-24) to the document context of the XML. |
| The XML names another profile | `<PdfFacturX> "profile" is "EN 16931", but the XML names "urn:factur-x.eu:1p0:minimum" (MINIMUM).` | Pass the profile that the XML names, or correct the XML. |
| `relationship` not allowed | `<PdfFacturX> requires "relationship" to be "Data", "Alternative" or "Source".` | Use one of the three values. |
| `relationship` not `'Data'` for `MINIMUM` or `BASIC WL` | `<PdfFacturX> "relationship" is "Alternative", but a MINIMUM invoice must use "Data": …` | Remove `relationship`. |
| `xml` is not text or bytes | `<PdfFacturX> "xml" must be a string or a Uint8Array with the file content.` | Pass the content, not a path or URL. |
| A second `PdfFacturX` | `<PdfDocument> may contain only one <PdfFacturX>.` | Keep one. |
| A `PdfAttachment` named `factur-x.xml` | `<PdfAttachment> "factur-x.xml" is the file name of <PdfFacturX>; choose another name.` | Rename the attachment. |
| `PdfFacturX` inside a page, or with content | `Invalid PDF nesting: …` | Put `PdfFacturX` directly in `PdfDocument`, without content. |

The failures of `PdfFacturX` with `invoice` are on the
[E-invoices]($docs.e-invoices#invalid-invoice-data) page.

## Evidence and limits

The repository tests PDF/A-3b output with veraPDF, the reference PDF/A
validator. Two test documents pass its PDF/A-3b profile: one with
registered-font text, umlauts, a running head with page numbers, a PNG with
transparency, an external link, a table over two pages, and attachments; one
Factur-X invoice with the `EN 16931` profile. The Factur-X PDFs are also
checked with Mustang; see
[E-invoices]($docs.e-invoices#evidence-and-limits). A document that uses features
outside these tests is expected to pass but is not proven. SVG text passes
only with its own `fontFamily` (see [Register a font for every text](#register-a-font-for-every-text)). Validate your own documents with veraPDF when an archive or a
recipient requires PDF/A. The PDF/A-3a evidence is on the
[Accessible PDF]($docs.accessible-pdf#evidence-and-limits) page.

Not claimed:

- the content of XML passed with `xml`: Nuxt PDF checks only that it is
  well-formed, has a `CrossIndustryInvoice` root and names the profile. The well-formedness check
  is a scan, not a validating parser: it does not read a DTD, resolve
  namespaces or check the characters of element names;
- PDF/A-3u (the Unicode level) and other PDF/A parts; for PDF/A-3a, see
  [Accessible PDF]($docs.accessible-pdf);
- that a PDF viewer shows the XML: veraPDF is the only evidence.

To read the embedded XML in a test, use `getPdfAttachments` from
[`@lupinum/nuxt-pdf/test`]($docs.test-utilities).
