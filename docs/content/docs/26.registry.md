Nuxt generates an inspectable `#pdf` module from the discovered templates. It is
a server-only module for Nitro code and is typed from each SFC's props. Do not
import it from a client component or other browser code.

```ts
import { pdf, renderPdf, pdfTemplateKeys } from '#pdf'
```

## pdf

`pdf` is an object keyed by template name. Property access infers each SFC's
props. Every value has exactly three public members:

```ts
interface PdfTemplate<Props extends object> {
  readonly key: string
  resolveMetadata(props: Props): {
    title?: string
    filename?: string
    language?: string
  }
  render(props: Props): Promise<PdfRenderResult>
}
```

The handle does not expose the compile-time definition, preview data, source
file, or a second preview render method.

```ts
await pdf.invoice.render({ invoice })
await pdf.report.render({ report })
```

Nested template paths keep their slash keys (for example
`pdf['reports/monthly']`).

## renderPdf

`renderPdf(name, props)` is the functional form. A **literal** template name
infers its props:

```ts
await renderPdf('invoice', { invoice })
```

A runtime string cannot be type-checked, so it requires the explicit
unknown-props escape hatch:

```ts
await renderPdf(templateName, untypedProps, { unsafe: true })
```

::warning{icon="lucide:triangle-alert"}
`{ unsafe: true }` does **not** validate the props; it only makes the loss of
static typing visible at the call site. An unknown template name still fails with
`PDF_TEMPLATE_NOT_FOUND`.
::

`pdfTemplateKeys` is the array of discovered template names.

`getPdfTemplate(name)` returns that typed three-member handle for a literal name,
or `undefined` for an unknown name. Reach for it when you need resolved
`definePdf` metadata without rendering:

```ts
import { getPdfTemplate } from '#pdf'

const template = getPdfTemplate('invoice')
const { title, filename } = template.resolveMetadata(props)
```

`resolveMetadata()` evaluates the `title` and `filename` declared by
`definePdf`, and returns its `language`. It does not mount the component, so a
title or language set on `PdfDocument` is not part of this result. A value that
`definePdf` sets is the same in `resolveMetadata()` and in `result.metadata`,
because a template cannot set it on `PdfDocument` too.

`NuxtPdfError` and `PDF_ERROR_CODES` are also re-exported from `#pdf`, so
server code can branch on render failures without extra imports. See
[Errors and limits]($docs.errors-and-limits).

## The render result

Both `pdf.name.render(props)` and `renderPdf(...)` resolve to a
`PdfRenderResult`. The document is rendered once; every conversion reuses that
completed, immutable byte buffer:

```ts
const result = await pdf.invoice.render({ invoice })

result.metadata        // frozen title, filename, and language for this render
await result.toUint8Array() // Promise<Uint8Array>
await result.toBuffer()     // Promise<Buffer>
await result.response()     // Promise<Response>
```

`result.metadata` is the frozen `title`, `filename`, and `language` resolved for
this render: each of `title` and `language` from `definePdf` or from
`PdfDocument`, whichever sets it (a template that sets one in both places
fails). `title` is written to the PDF Info dictionary and `language` to the catalog
`/Lang` entry; `filename` is response/download metadata and is not written
into the PDF.
`result.diagnostics` is one frozen object shared with the development preview:

| Field | Meaning |
| ----- | ------- |
| `durationMs` | Wall time for the whole public render, including metadata evaluation |
| `byteLength` | Exact output byte count |
| `pageCount` | Number of rendered pages |
| `passes` | Layout passes used (`1` normally, `2` or more with `PdfPageRef`, an in-flow `pages="first"` node, or a header moved by the orphan rule) |
| `layoutWarnings` | Frozen, structured warnings for layout that rendered but needs attention |
| `imageWarnings` | Frozen entries for rich text images that printed a placeholder because their source was refused |
| `richTextWarnings` | Frozen entries for rich text input that `PdfRichText` dropped or changed, one per code and name |
| `registeredFontFaces` | Frozen family/weight/style facts; never source bytes or paths |

Diagnostics contain no document content, props, or resource URLs in
production. An application can send them to its metrics layer. Only
development builds add source positions and the `snippet` of a rich text
warning.

`layoutWarnings` is empty for a healthy layout. Each `PdfLayoutWarning` has a
`code` that says which fields it has, so check `code` before reading the other
fields:

- `PDF_UNBREAKABLE_NODE_OVERFLOW`: a node that is not fixed or absolute cannot
  wrap and is taller than the page's usable content height. This includes a block that the engine
  shrank to fit the page; its `nodeHeight` is the height the block needs, and
  the rows that a cell with `rowspan` holds together (`nodeType` `'PdfView'`,
  `availableHeight` without the repeated header rows). The
  warning has `pageNumber`, `nodeType`, `nodeHeight` and `availableHeight`, in
  points. Allow the node to wrap or make it small enough to fit on one page.
- `PDF_CONTENT_HIDDEN`: content is cut off and not drawn. A text keeps only
  the lines that fit its `height` or `maxHeight`, or the height of a view
  with a `height` or `maxHeight` around it. An absolute node can also reach
  below the page end. The warning comes once per node and has `pageNumber`,
  `nodeType` (the text, or the absolute node), `hiddenLines` (the text lines
  that are not drawn) and `hiddenNodes` (the images, SVGs and other boxes of
  an absolute node below the page; `0` for a text). Give the box more height,
  shorten the content, or move the absolute node up. Inside a block that
  reports `PDF_UNBREAKABLE_NODE_OVERFLOW`, only that warning comes.
- `PDF_TABLE_COLUMNS_TOO_NARROW`: a `PdfTable` with `'auto'` columns is
  narrower than its columns need to keep their longest words whole and to
  hold the padding of their cells, so some words break or run over their
  column, and a padded cell can push the cells after it. The warning comes once per table and
  has `pageNumber` (the page where the table starts), `tableWidth` and
  `neededWidth`, in points. Give the table more room or shorten the longest
  words.
- `PDF_FOOTNOTES_MOVED`: the notes of a page did not all fit on it with their
  marks, so some print first in the note area of the next page. The warning
  comes once per page and has `pageNumber` (the page of the marks) and
  `footnotes` (the numbers of the notes that moved, in order). Let the block
  with the marks wrap, or shorten the notes.
- `PDF_GLYPH_MISSING`: a character is in no font of its text, so it shows as
  the font's empty box (`.notdef`) and copies as U+FFFD. The warning comes
  once per character and has `pageNumber` (the first page with it),
  `codePoint` and `fontFamily` (the family the text asks for). Register a
  font that contains it and use it in `fontFamily`, or replace the character.
- `PDF_KEEP_IGNORED`: a `keepWithNext` chain or a `minPresenceAhead` could
  not hold, so the nodes break as without it: the node and what it keeps
  are higher than the page's content area, or the node starts a page, where
  a move gains nothing. The warning comes once per chain and has
  `pageNumber` (the first page where the keep is dropped) and `nodeType`
  (the first node of the chain). Shorten the chain of nodes that keep
  together, or remove the keep.
- `PDF_HYPHENATION_UNAVAILABLE`: a text has `hyphens: 'auto'`, but Nuxt PDF
  has no hyphenation patterns for the document `language`, so words split only
  at their soft hyphens. It has
  `language`. Set a supported tag, such as `de` or `en-GB`, or put soft
  hyphens (`&shy;`) in long words. Languages whose writing does not hyphenate,
  such as Arabic, Chinese or Japanese, give no warning.

No warning copies text or ids from the document, apart from the code point of
a missing character and the document language. In development a warning about
a node also carries `source`, the template position of the node (see
[source positions]($docs.errors-and-limits)).

`imageWarnings` is empty unless a `PdfRichText` image source was refused. Each
entry is a `PdfImageWarning` with `code` `PDF_RICH_TEXT_IMAGE_REPLACED`, the
`reason` (`PDF_ASSET_BLOCKED` or `PDF_ASSET_INVALID`), the `path` of the image in
the rich text model, and in development `source`. It does not contain the
image source. See [broken images]($docs.rich-text#broken-images).

`richTextWarnings` is empty unless `html` or `comark` input of a `PdfRichText`
lost something: a link, an attribute, a tag, a value, a component or a prop.
Each `PdfRichTextWarning` has `code`, `name` (the tag, attribute, link kind or
`component.prop`), `message` and `count`; in development also `snippet` and
`source`. See [dropped input]($docs.rich-text#dropped-input).

## Development and production boundary

The development preview keeps `sampleData`, named `scenarios`, and the relative
source file outside the public template handle. It calls the same public
`render(props)` method as application code and displays that completed result.
There is no separate preview renderer or second document render. Only the
**Layout boxes** toggle renders the template with layout boxes drawn, for the
preview alone.

Editing a template rebuilds its registry and refreshes the document with its
diagnostics. The preview keeps the selected scenario.

In a production build the SFC transform reconstructs the render definition from
only `title`, `filename`, `language`, and `maxPasses`. `sampleData` and
`scenarios` are structurally omitted before Nitro bundles the template; they are
not public handle properties and are not merely hidden behind runtime checks.
The development preview data and routes are also absent. The renderer and the template files are not in the client output.

Metadata is hoisted: inline values and imports are supported, while references
to bindings declared locally in `<script setup>` are compile errors. Imported
preview-data modules must be side-effect-free so their unused production imports
can be eliminated.

### response(init)

`response()` returns a `Response` with `content-type: application/pdf`, the
exact `content-length`, and a sanitized, encoded-length-bounded
`content-disposition` filename:

```ts
await result.response({
  disposition: 'inline',      // 'attachment' (default) | 'inline'
  filename: 'invoice.pdf',    // sanitized before writing the header
  headers: { 'cache-control': 'no-store' },
})
```

| Field | Type | Description |
| ----- | ---- | ----------- |
| `disposition` | `'attachment' \| 'inline'` | `content-disposition` type; defaults to `attachment` |
| `filename` | `string` | Download filename; sanitized before use; defaults to template metadata or `document.pdf` |
| `headers` | `HeadersInit` | Extra response headers merged in |
| `status`, `statusText` | `number` / `string` | Standard `ResponseInit` fields |

Caller-provided `content-type`, `content-length`, and `content-disposition`
headers are replaced with the values of the completed result.

## Regenerating the registry

The registry is written during module setup and regenerated whenever templates
change in development. If `#pdf` imports appear untyped in your editor, run
`nuxt prepare` once to refresh the generated types.
