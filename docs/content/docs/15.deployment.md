Nuxt PDF renders on Node. The engine, the templates, and the embedded assets
live in the Nitro server output. The client bundle contains none of them.
For a separate Node worker, use the
[standalone registry build]($docs.standalone-node).

## Pick a runtime

| Runtime | Support | Notes |
| ------- | ------- | ----- |
| Node server (default Nitro preset) | Supported | The tested path. Use it for high-volume or large documents. |
| Standalone Node registry | Locally tested | Compile with the build entry. Test the deployed worker before production use. |
| Convex Node action | Not deployment-verified | A candidate for the standalone registry. Measure bundle size, memory, and execution limits on the target deployment. |
| Vercel serverless build | Build-verified | The package tests build the Vercel preset locally. No test executes the deployed function. Execute it before production use. |
| Other Node serverless functions | Expected, not verified | Use a Node-compatible Nitro preset and test the deployed runtime. |
| Edge workers | Not supported | The engine needs Node APIs. Do not target edge presets. |

## Render workers

Layout and PDF writing run in a pool of worker threads. The request handler
stays responsive while a large document lays out.

- **Pool size.** One fewer than the available CPU cores, at least 1 and at
  most 4. Renders beyond the pool size wait in a first-in, first-out queue.
- **Memory.** Each worker has a JavaScript heap limit of 1024 MB. Image
  buffers are held outside that heap. A worker that runs out of memory fails
  its render and leaves the pool; the next render starts a fresh worker.
- **Idle workers.** A finished worker stays warm for the next render. Idle
  workers do not keep the Node process alive. An idle worker that fails
  leaves the pool and does not stop the server.
- **Restarts.** A worker is replaced after 200 renders, so engine caches do
  not grow without bound.
- **Deadline.** `pdf.limits.timeoutMs` counts the wait in the queue and the
  render. At the deadline the worker is stopped, also in the middle of a long
  layout, and the render fails with `PDF_LIMIT_EXCEEDED`.

The pool has no module option.

### In-process rendering

Some Nitro presets bundle the whole server into one file. Such a build has no
separate worker file, so renders run in the server process. The build logs
this warning:

```text
nuxt-pdf: this Nitro preset bundles the server into one file, so PDFs render in-process. The render deadline is then checked between engine stages and cannot stop a long layout.
```

In-process renders produce the same bytes. A long layout blocks the server
process until it ends. Prefer a preset that keeps separate server chunks, such
as the default Node server preset.

## Size the memory budget

Give each function or container headroom for every worker that renders at the
same time:

- Plan for up to four workers with a 1024 MB heap each, plus image buffers.
- Lower `pdf.limits.maxPages`, `pdf.limits.maxTotalImageBytes`, and
  `pdf.limits.maxTotalImagePixels` to cap the worst case for untrusted input.
- Load-test with your real templates before you pick an instance size.

See [pdf.limits]($docs.module-options#pdflimits) for every limit and its
default.

## Align timeouts

The render deadline lives in `pdf.limits.timeoutMs` (30 seconds by default).
The platform timeout must stay longer than that budget, or the platform kills
a render that Nuxt PDF would have finished.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  pdf: {
    limits: {
      timeoutMs: 10_000,
    },
  },
})
```

Set the platform function timeout to at least the same value plus queueing
headroom.

## Cache completed renders

Cache a PDF only when your application controls every input to the render. A
template can read the current time or imported application code. An allowlisted
remote image can also change without a props change. Nuxt PDF does not promise
that these renders produce the same bytes.

Build the cache key from the template version and the canonical render inputs.
Include the tenant or authorization boundary when documents differ between
customers. Store the completed bytes in a bounded cache, object store, or CDN
with an explicit expiry and invalidation rule.

Do not use a module-level `Map` as a production cache. It has no size limit,
does not persist reliably across serverless invocations, and can cross request
boundaries when its key is incomplete.

## Queue long documents

A 200-page report can occupy a worker for seconds. Keep that work off the
request path when you can:

1. Accept the request and return a job identifier.
2. Render in a background worker.
3. Store the bytes and let the client poll or subscribe.

This pattern also keeps interactive routes responsive while batch jobs run.

## Serverless notes

Local fonts and images travel inside the server bundle as validated bytes. The
package tests run on the Node server preset and build the Vercel preset
locally. No test runs a deployed serverless function, so render workers on a
real serverless runtime are not verified. Test the real target before you send
production traffic.

- **Bundle size.** Every font and image under `pdfs/` adds to the bundle.
  Remove assets that no template uses; the module embeds only discovered
  files.
- **Cold starts.** The first invoke parses the bundle. Fewer embedded assets
  mean faster cold starts. A fresh instance also starts its first render
  worker; that start time on a small instance is not measured.
- **Concurrency.** One instance renders up to four documents at the same time
  (see [Render workers](#render-workers)). Size instance concurrency from load
  tests on your deployed runtime.
- **Filesystem access.** Templates read no files at runtime. Do not add code
  that reads from the deployment filesystem during a render.

## Monitor renders

Every render returns content-free diagnostics: duration, byte length, page
count, layout passes, layout warnings, and registered font faces. Log them next
to your request logs to spot slow or oversized documents before users do.

```ts [server/api/invoice.get.ts]
export default defineEventHandler(async () => {
  const result = await pdf.invoice.render(props)
  console.info('invoice rendered', result.diagnostics)
  return result.response()
})
```
