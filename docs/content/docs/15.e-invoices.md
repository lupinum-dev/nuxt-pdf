An e-invoice is an invoice that software can read. The European standard
EN 16931 defines its data. Nuxt PDF writes the e-invoice XML (UN/CEFACT CII
syntax) from one invoice object, the `EInvoice`. There are two forms:

- A **Factur-X invoice** (in Germany: ZUGFeRD 2) is a PDF/A-3b document with
  the XML inside. A person reads the pages, and accounting software reads the
  XML. `PdfFacturX` with `invoice` writes it.
- An **XRechnung** is the German EN 16931 profile. German public buyers
  usually want the XML alone. `renderEInvoiceXml` writes it on the server.

Use the `EN 16931` profile for a Factur-X invoice unless your recipient asks
for another one. See [Profiles](#profiles).

## Write a Factur-X invoice

A Factur-X invoice is a PDF/A-3b file: set `conformance="PDF/A-3b"` on
`PdfDocument`. Without a PDF/A-3 level, the render fails. Every text then needs
a registered font. Register one in `pdf.fonts` and set `fontFamily` on every
page. See
[Register a font for every text]($docs.pdf-a-and-factur-x#register-a-font-for-every-text).

Pass the invoice data to `PdfFacturX` with `invoice`, and print the totals
from `computeEInvoice`:

```vue [pdfs/invoice.vue]
<script setup lang="ts">
import type { EInvoice } from '@lupinum/nuxt-pdf'

interface Props {
  invoice: EInvoice
}

definePdf<Props>({
  title: props => `Invoice ${props.invoice.number}`,
  filename: props => `invoice-${props.invoice.number}.pdf`,
})

const props = defineProps<Props>()
const totals = computeEInvoice(props.invoice)
</script>

<template>
  <PdfDocument language="en" conformance="PDF/A-3b">
    <PdfFacturX :invoice="invoice" profile="EN 16931" />
    <PdfPage size="A4" :style="{ fontFamily: 'Invoice Sans' }">
      <PdfText>Invoice {{ invoice.number }}</PdfText>
      <PdfView v-for="(line, index) in invoice.lines" :key="index">
        <PdfText>{{ line.name }}: {{ totals.lines[index]!.netAmount }} {{ invoice.currency }}</PdfText>
      </PdfView>
      <PdfText>Net: {{ totals.taxBasisTotal }} {{ invoice.currency }}</PdfText>
      <PdfText v-for="vat in totals.vatBreakdown" :key="`${vat.category}-${vat.rate}`">
        VAT {{ vat.rate ?? 0 }} %: {{ vat.taxAmount }} {{ invoice.currency }}
      </PdfText>
      <PdfText>Amount due: {{ totals.duePayable }} {{ invoice.currency }}</PdfText>
    </PdfPage>
  </PdfDocument>
</template>
```

During the render, the server checks the invoice data and writes the XML for
the profile of `PdfFacturX`. The XML holds the same totals that
`computeEInvoice` returns, so the pages and the XML show the same amounts.
`computeEInvoice`, `validateEInvoice`, and `renderEInvoiceXml` are available
in every template and component under `pdfs/` without an import.

Render the template like any other template:

```ts [server/api/invoice.get.ts]
import { pdf } from '#pdf'
import { loadInvoice } from '../utils/invoices'

export default defineEventHandler(async (event) => {
  const invoice = await loadInvoice(String(getQuery(event).number))
  const result = await pdf.invoice.render({ invoice })
  return result.response()
})
```

## Invoice data

The `EInvoice` object holds the invoice. The comments of each field name its
EN 16931 business term, such as BT-1 for the invoice number. This invoice is
valid for every profile, `XRECHNUNG` included:

```ts [server/utils/invoices.ts]
import type { EInvoice } from '@lupinum/nuxt-pdf'

export const exampleInvoice: EInvoice = {
  number: 'RE-2026-014',
  issueDate: '2026-11-03',
  currency: 'EUR',
  // The Leitweg-ID of a German public buyer. XRechnung requires it.
  buyerReference: '991-01234-56',
  seller: {
    name: 'Beispiel Werkstatt GmbH',
    address: { line1: 'Beispielweg 1', postcode: '10115', city: 'Berlin', country: 'DE' },
    vatId: 'DE111111111',
    contact: { name: 'Erika Beispiel', phone: '+49 30 0000000', email: 'billing@werkstatt.example' },
    electronicAddress: { email: 'invoices@werkstatt.example' },
  },
  buyer: {
    name: 'Stadtverwaltung Musterstadt',
    address: { line1: 'Rathausplatz 2', postcode: '50667', city: 'Köln', country: 'DE' },
    electronicAddress: { email: 'rechnungen@musterstadt.example' },
  },
  payment: {
    dueDate: '2026-12-03',
    means: { type: 'sepa-credit-transfer', iban: 'DE02120300000000202051' },
  },
  lines: [
    { name: 'Design workshop', quantity: 2, unit: 'day', netPrice: '950.00', vat: { category: 'standard', rate: 19 } },
    { name: 'Printed brochures', quantity: 500, unit: 'piece', netPrice: '1.20', vat: { category: 'standard', rate: 7 } },
  ],
}

// Replace this with the query of your database.
export const loadInvoice = async (number: string): Promise<EInvoice> => ({ ...exampleInvoice, number })
```

- **Amounts, quantities and rates** are a number or a decimal string, such as
  `'950.00'`. Use strings for money from a database or a form: a string keeps
  every digit, and a number such as `0.1` is not exact.
- **Dates** are `YYYY-MM-DD` strings.
- **Units** are a name (`'piece'`, `'hour'`, `'day'`, `'kilogram'`, `'metre'`,
  `'lump-sum'`, and more) or a UN/ECE code, such as `{ code: 'XPK' }`.
- **VAT** of a line is one category: `'standard'` with a `rate` in percent,
  `'zero'`, `'exempt'` with an `exemptionReason`, `'reverse-charge'`,
  `'intra-community'`, `'export'`, or `'outside-scope'`.

## Totals

`computeEInvoice(invoice)` returns the totals by the EN 16931 rules. Each
amount is a decimal string with two fraction digits. For the invoice above:

| Field | Meaning | Value |
| --- | --- | --- |
| `lines[i].netAmount` | Quantity × price of line `i`, with its allowances and charges | `'1900.00'`, `'600.00'` |
| `vatBreakdown` | One entry for each VAT category and rate: `taxableAmount`, `taxAmount` | 19 %: `'361.00'`, 7 %: `'42.00'` |
| `lineTotal` | Sum of the line net amounts | `'2500.00'` |
| `allowanceTotal`, `chargeTotal` | Sums of the document allowances and charges | `'0.00'` |
| `taxBasisTotal` | Total without VAT | `'2500.00'` |
| `taxTotal` | Total VAT | `'403.00'` |
| `grandTotal` | Total with VAT | `'2903.00'` |
| `prepaidAmount`, `roundingAmount` | The paid amount and the rounding of the invoice | `'0.00'` |
| `duePayable` | Amount due for payment | `'2903.00'` |

The VAT of each category is rounded once, on its total, not on each line.
Print these values instead of your own sums, so the pages agree with the XML.
`computeEInvoice` throws `PDF_INVOICE_INVALID` when a value cannot be read, for
example a quantity `'2,5'`.

## Profiles

A profile sets how much of the invoice the XML holds. `PdfFacturX` and
`renderEInvoiceXml` take one of these:

| `profile` | The XML holds | An e-invoice in Germany |
| --- | --- | --- |
| `'MINIMUM'` | The parties and the totals, no lines | No |
| `'BASIC WL'` | `MINIMUM` with VAT breakdown, allowances and payment, no lines | No |
| `'BASIC'` | The lines and the most used EN 16931 fields | Yes |
| `'EN 16931'` | All EN 16931 fields that `EInvoice` has | Yes |
| `'XRECHNUNG'` | `EN 16931` with the German rules (XRechnung 3.0) | Yes |

Since 2025, German businesses must be able to receive e-invoices. From 2027,
businesses with more than EUR 800,000 turnover must issue them for domestic B2B
sales, and from 2028 all businesses. `MINIMUM` and `BASIC WL` hold no lines, so
they do not meet the German requirement.

`'XRECHNUNG'` adds these requirements:

- `buyerReference`, the Leitweg-ID for a public buyer;
- a seller `contact` with `name`, `phone`, and `email`;
- a postcode and city for the seller and the buyer;
- `electronicAddress` for the seller and the buyer;
- `payment.means`;
- a VAT ID (`vatId`) or tax number (`taxNumber`) for the seller, when the VAT
  category needs one;
- a city and post code if you give `delivery.address`;
- the payment details of a card or direct debit.

A Factur-X PDF with `'XRECHNUNG'` embeds the XML as `xrechnung.xml`. The
other profiles use `factur-x.xml`.

`EXTENDED` is not available with `invoice`. To embed EXTENDED XML that your
application writes, use `PdfFacturX` with `xml`. See
[Add the XML invoice]($docs.pdf-a-and-factur-x#add-the-xml-invoice).

## Check form input

Call `validateEInvoice` before you save invoice data, for example in the route
that receives a form. It returns every problem at once and does not throw for
invalid data:

```ts [server/api/invoices.post.ts]
import { validateEInvoice } from '#pdf'
import type { EInvoice } from '@lupinum/nuxt-pdf'

export default defineEventHandler(async (event) => {
  const invoice = await readBody<EInvoice>(event)
  const issues = validateEInvoice(invoice, { profile: 'XRECHNUNG' })
  if (issues.length > 0) {
    throw createError({ statusCode: 422, data: { issues } })
  }
  // Save the invoice.
})
```

Each issue is an `EInvoiceIssue` with three fields:

| Field | Example | Meaning |
| --- | --- | --- |
| `rule` | `'BR-DE-15'` | The rule ID of EN 16931 (`BR-…`), XRechnung (`BR-DE-…`), the Peppol rules of XRechnung (`PEPPOL-EN16931-…`), or Nuxt PDF (`PDF-…`). |
| `path` | `'invoice.buyerReference'` | The field. Use it to show the message next to the form field. |
| `message` | `'XRechnung needs the buyer reference, …'` | What is wrong and which field to give. |

An empty list means that `PdfFacturX` and `renderEInvoiceXml` accept the
invoice for that profile. `validateEInvoice` does not check
the IBAN checksum.

## Write an XRechnung XML

`renderEInvoiceXml` returns the XML as a string. Send it as the response, or
store it:

```ts [server/api/invoice-xml.get.ts]
import { renderEInvoiceXml } from '#pdf'
import { loadInvoice } from '../utils/invoices'

export default defineEventHandler(async (event) => {
  const number = String(getQuery(event).number)
  const invoice = await loadInvoice(number)
  setHeader(event, 'content-type', 'application/xml; charset=utf-8')
  setHeader(event, 'content-disposition', `attachment; filename="${number}.xml"`)
  return renderEInvoiceXml(invoice, { profile: 'XRECHNUNG' })
})
```

`renderEInvoiceXml` checks the invoice with `validateEInvoice` first. It throws
`PDF_INVOICE_INVALID` when the list has an issue. It does not need a template or
a render. Outside Nuxt, import it from `@lupinum/nuxt-pdf/server`.

## Invalid invoice data

Invalid invoice data fails with `NuxtPdfError` and the code
`PDF_INVOICE_INVALID`, from `renderEInvoiceXml` and from a render with
`PdfFacturX`. `error.issues` holds the same list that `validateEInvoice`
returns. The message lists every issue:

```text
The invoice breaks a rule of XRECHNUNG:
- BR-DE-15 at invoice.buyerReference: XRechnung needs the buyer reference, for a public buyer the Leitweg-ID. Give invoice.buyerReference.
```

```ts [server/api/invoice.get.ts]
import { NuxtPdfError, PDF_ERROR_CODES, pdf } from '#pdf'
import { loadInvoice } from '../utils/invoices'

export default defineEventHandler(async (event) => {
  const invoice = await loadInvoice(String(getQuery(event).number))
  try {
    const result = await pdf.invoice.render({ invoice })
    return result.response()
  }
  catch (error) {
    if (error instanceof NuxtPdfError && error.code === PDF_ERROR_CODES.InvoiceInvalid) {
      throw createError({ statusCode: 422, data: { issues: error.issues } })
    }
    throw error
  }
})
```

Correct the field that each `path` names. The render fails before the
layout, so no PDF exists.

These mistakes in the template fail with `PDF_TREE_INVALID` and the source
position:

| Cause | Message | Inspect or change |
| --- | --- | --- |
| Both `xml` and `invoice` | `<PdfFacturX> has both "xml" and "invoice". …` | Keep one. |
| Neither `xml` nor `invoice` | `<PdfFacturX> requires "invoice" (the invoice data) or "xml" (the finished CII XML).` | Pass the invoice data with `invoice`. |
| `EXTENDED` with `invoice` | `<PdfFacturX> cannot write the EXTENDED profile from "invoice". …` | Use another profile, or pass the EXTENDED XML with `xml`. |
| `invoice` is not an object | `<PdfFacturX> "invoice" must be the invoice data object.` | Pass the `EInvoice` object. |

## Validate your invoices

Validate sample invoices of your application with the validators that
recipients use. The repository runs both with Java 17:

- **Mustang** checks a Factur-X PDF (the PDF/A part and the XML) and CII XML.
  Download the Mustang CLI from mustangproject.org.
- The **KoSIT validator** with the XRechnung configuration checks XRechnung
  XML. Download both from the KoSIT pages on GitHub.

```bash
java -jar Mustang-CLI-2.26.0.jar --action validate --source invoice.pdf
```

```bash
java -jar validator-1.6.3-standalone.jar -s xrechnung-config/scenarios.xml -r xrechnung-config -o reports invoice.xml
```

Read every `summary` element of the Mustang report. For a PDF, the report has
one summary for the PDF part and one for the XML. Mustang can report the file
as valid and exit with code 0 while the PDF part is invalid. The KoSIT
validator writes `Acceptable` or `Rejected` and a report for each file.

## Limits

The repository checks the output with Mustang 2.26.0 and the KoSIT validator
1.6.3 with the XRechnung 3.0.2 configuration of 2026-08-31:

- the XML of the fixed invoices in every profile in Mustang, and `XRECHNUNG`
  also in the KoSIT validator, and of 40 generated invoices. The invoices cover several VAT
  rates, zero-rated and exempt lines, reverse charge, intra-community supply,
  export, allowances and charges, credit notes, and each payment means;
- a rendered Factur-X PDF for each profile, and one with XML passed in `xml`:
  Mustang accepts the PDF/A-3b part and the XML;
- invalid data that each validator must reject, so a check that cannot fail
  is found.

The validators do not check that a line amount equals quantity × price. The
unit tests of `computeEInvoice` check it.

Not claimed:

- UBL, the other EN 16931 syntax: Nuxt PDF writes only CII;
- writing the `EXTENDED` profile;
- the IBAN checksum, and that an ID such as a VAT ID or a Leitweg-ID exists;
- that the printed pages agree with the XML when the template prints other
  values than `computeEInvoice` returns;
- every EN 16931 field: `EInvoice` has no fields for item attributes,
  invoiced objects, or additional documents, for example.

Mustang does not compare the profile in the PDF metadata with the profile of
the XML. Nuxt PDF writes the metadata from the same `profile` that writes the
XML, and with `xml` it checks that the XML names that profile.
