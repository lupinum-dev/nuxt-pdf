How content splits across pages. The props are listed on
[Primitives]($docs.primitives).

## Fixed content and pages

A `fixed` node repeats on every page of its parent. The parent is the
`PdfPage` for a node directly on the page (every page that page breaks into),
and the view that holds the node for a nested node (every page that view
reaches). A table header is a `fixed` row of its table. Page tokens in a
`fixed` node print the values of the page it repeats on, in a nested node too.

A `fixed` node after the last flow node of its parent, such as a `fixed`
row written after the rows of a table or a footer written last on the page,
ends every page of the parent, right below the content of that page. The
flow breaks early enough to leave its height free, so the rows above it keep
their height. If that room holds none of the flow and nothing else is above
the parent on the page, for example below a tall `fixed` view, the flow
breaks at the page end instead and the page squeezes it to fit the fixed
node. Rows that one cell spans and that fit only up to the page end stay on
the page the same way.

Put a `fixed` node before the flow of its `PdfPage` or view (a header) or
after it (a footer written last). One between flow content fails with
`PDF_LAYOUT_ERROR`: on a page that ends before it, the content of that page
would be squeezed to make room for it. An absolute `fixed` node takes no room
and can stand anywhere among the children. In a row, a `fixed` cell stands
beside the other cells, and a `fixed` or `:wrap="false"` view never breaks, so
the order of their children does not matter.

`PdfView` and page-flow `PdfText` also accept `pages`, which limits the pages
of the parent on which a `fixed` node appears:

| `pages` | Appears on |
| ------- | ---------- |
| `'all'` (default) | Every page of its parent. |
| `'first'` | The first page of its parent only. |
| `'continuation'` | Every page of its parent except the first. |
| `'not-last'` | Every page of its parent except the last. |

```vue
<PdfText fixed pages="continuation">
  {{ document.title }} · <PdfPageNumber />
</PdfText>
```

A `'first'` or `'continuation'` node takes room only on the pages where it
appears: the other pages of the parent hold as much content as a page without
it. A `'not-last'` node takes room on every page of its parent, because the
last page is known only after it is filled; the last page keeps that room
empty. None of this costs an extra layout pass.

Fixed content must leave room for the content after it. When the `fixed`
nodes above some content are together as high as the page content area or
higher, the render fails at once with `PDF_LAYOUT_ERROR`. The message names
the node, its source position, its height, the room on the page, and the pages
that are full: every page, the first page, or every page after the first. The
first page counts the `'continuation'` nodes too, because it breaks as if they
were there. Make the fixed content lower, give it `position: 'absolute'`, or
remove `fixed` so it can break across pages.

An SVG, image or canvas never breaks across pages. When such a block is
higher than the room that fixed content leaves, it stays where it starts, cut
at the page end, and the render gives the layout warning
`PDF_UNBREAKABLE_NODE_OVERFLOW`. When content can never fit below or beside
fixed content, so that two pages in a row take nothing from the flow, the
render fails with `PDF_LAYOUT_ERROR` ("Pagination cannot end"). A `fixed`
node in a row repeats beside the row's content on every page the row reaches,
and the row ends with its content. A row with `flexWrap` breaks between its
lines, and a line that crosses the page end splits as a row. A `fixed` item of
a wrapping row has no place of its own on the next page, so it fails with
`PDF_LAYOUT_ERROR` when the row breaks: put the `fixed` node before the row.

For a running head, the recommended pattern is an absolute `fixed` node in the
page padding. It takes no space in the flow, so no page loses content and no
extra pass runs:

```vue
<PdfPage size="A4" :style="{ paddingTop: 64, paddingHorizontal: 48, paddingBottom: 48 }">
  <PdfText
    fixed
    pages="continuation"
    :style="{ position: 'absolute', top: 28, left: 48, right: 48, fontSize: 8 }"
  >
    {{ document.title }} · <PdfPageNumber />
  </PdfText>
  <PdfText>{{ document.body }}</PdfText>
</PdfPage>
```

`pages` counts the pages of one parent. A running head that must continue on
a second `PdfPage` uses `pages="all"` on that page.

Rules, each enforced with `PDF_TREE_INVALID`:

- `pages` requires `fixed`.
- A node with `pages` other than `'all'` contains only `PdfView`, `PdfText`,
  text, and page tokens. It cannot contain a `bookmark` or another `pages` node.
- `pages` is not supported on a `PdfText` nested inside another `PdfText`.

A view with `fixed` children and other children does not end a page with only
its `fixed` children. When a page would end with a repeated header alone, the
view starts on the next page instead. In a column container, it starts the next
column, and after the last column the next page. This costs one extra layout
pass.

## Page breaks

`break` starts a new page before its node at every depth: on a node directly
on the page, and on a node inside one or more views, also when those views fit
on the page. The rest of each view around the node continues on the next page,
without its top padding and top border. When the node is the first content of
its view, the whole view moves to the next page.

A `break` with only `fixed` content before the node on its page is ignored,
so a break never adds an empty page.

A `break` in these places fails the render with `PDF_TREE_INVALID`, because it
could not start a page there. The message names the element and the ancestor
that prevents the break:

- Inside a row (`flexDirection: 'row'` or `'row-reverse'`), and inside a table
  row or cell. The children of a row sit side by side, so a break cannot end
  the page for one of them only. Put the `break` on the row, or on the
  `PdfTableRow`.
- Inside a node with `:wrap="false"`. That node stays whole on one page.
  Remove `:wrap="false"`, or remove the `break`.
- Inside a `fixed` node, such as a `PdfTableHeader`, which repeats on every
  page. Remove the `break`.

The row itself, a `PdfTableRow` and a node with `:wrap="false"` can have a
`break`: it applies to the whole node.

`break="column"` starts the next column, or the next page after the last
column, and fails in the same places. See [Columns]($docs.styles#columns).

A node that moves whole to the next page keeps its top margin, at every depth:
after an automatic page break and after `break`. The continuation part of a
node that splits across pages starts with no top margin, top padding or top
border. A node that fits on the page stays there when its bottom margin does
not: the margin is dropped at the break, also inside views and columns, and the
content after it starts the next page. With `minPresenceAhead` the margin
counts, and the space the node asks for starts below it. So space between
blocks set as `marginBottom` never shows at a page end, as in CSS; set as
`marginTop` on the next block, it stays at the top of the next page. A negative
top margin reaches above the content area only where you put the node at the
page top: on the first page and after `break`, for example to let a banner
reach into the page padding. After an automatic page break it pulls a node no
higher than the top of the content area.

## Keep with the next node

`keepWithNext` moves a node to the next page when the start of the node after
it does not fit on the page. Put it on a heading to keep the heading with its
paragraph or table:

```vue
<template>
  <PdfText class="h2" keep-with-next>Line items</PdfText>
  <PdfTable :columns="[1, '80pt']">
    <PdfTableRow v-for="line in lines" :key="line.id">
      <PdfTableCell>{{ line.title }}</PdfTableCell>
      <PdfTableCell align="right">{{ line.total }}</PdfTableCell>
    </PdfTableRow>
  </PdfTable>
</template>
```

The start of the next node is:

- for a node that does not split (a table row, a node with `:wrap="false"`,
  an image), the whole node;
- for a text, the lines it needs to start a page: its `orphans` (2 by
  default), or all of its lines when it has fewer than `orphans` plus
  `widows`;
- for a view or a table, the start of its first node that shows content, so
  a heading keeps a table's first row and the header above it. When that
  first node has `keepWithNext` too, what it keeps counts as well;
- for a view in row direction, the latest start of its children that show
  content;
- for a view without content, its whole box when it paints a background or
  a border.

`keepWithNext` keeps a node with the next node in the same container.
`fixed` and absolute nodes are skipped, and so are nodes that show nothing
and paint nothing, such as an anchor `<PdfView id="totals" />`. A node with
`:fixed="false"` is in the flow and keeps like any other node. When the next
node has `break`, the keep has no effect, as that node starts a new page
anyway.

When the next node has `keepWithNext` too, the keep continues to the node
after it, so a title, a subtitle and a paragraph stay together. When the node
and what it keeps are higher than the page, the keep has no effect, and the
nodes split across pages as without it. This counts the whole chain: when
every row of a long table keeps with the next, the rows split as without the
keep until the rest of the chain fits one page, and that rest moves to the
next page as one block. A keep that has no effect gives the
[layout warning]($docs.registry#the-render-result) `PDF_KEEP_IGNORED`, once
per chain.

On a `PdfTableRow`, `keepWithNext` keeps the row with the next row. On the
last row of a table, it keeps the row with the node after the table, as
`break-after: avoid` does in CSS. Use it to keep the last item with the
totals:

```vue
<template>
  <PdfTable :columns="[1, '80pt']">
    <PdfTableHeader>
      <PdfTableCell>Item</PdfTableCell>
      <PdfTableCell align="right">Total</PdfTableCell>
    </PdfTableHeader>
    <PdfTableRow
      v-for="(line, index) in lines"
      :key="line.id"
      :keep-with-next="index === lines.length - 1"
    >
      <PdfTableCell>{{ line.title }}</PdfTableCell>
      <PdfTableCell align="right">{{ line.total }}</PdfTableCell>
    </PdfTableRow>
  </PdfTable>
  <PdfView :wrap="false" class="totals">
    <PdfText>Total: {{ total }}</PdfText>
  </PdfView>
</template>
```

When the totals do not fit below the table, the table splits before its
last row, and that row moves to the next page with the totals, under the
repeated header. The rest of the table stays where it is.

The same holds for the last node of any view: the view splits before that
node, before the nodes that keep with it, and before the rows that a cell
over several rows holds together with it. That tail moves with the node
after the view, also when only the view's bottom padding and border cross
the page end. A paragraph in the tail moves whole, as with its own keep.
The whole view moves only when the tail is all its content, as in
`<PdfView><PdfText keep-with-next>Title</PdfText></PdfView>`, or when the view
has `:wrap="false"`. Nodes after the tail that show nothing, such as an
anchor, do not count.

`keepWithNext` in these places fails the render with `PDF_TREE_INVALID`,
because the node has no next node to start with:

- On a `PdfPage`, which always starts a new page.
- On a `fixed` node, which repeats on every page.
- On a `PdfText` inside another `PdfText`. Put it on the outer text.
- Inside a row (`flexDirection: 'row'` or `'row-reverse'`). Its children sit
  side by side. Put it on the row.
- Inside a `flexDirection: 'column-reverse'` container. The next node in the
  tree is drawn above, not after.
- Inside a `PdfTableCell`. The cells of a row move to the next page together.
  Put it on the `PdfTableRow`.

`minPresenceAhead` asks for space in points instead of for the next node. The
space starts below the node's bottom margin. It reaches at most to the end of
the last flow node after it in the same container, so with `120` and 40 pt of
content after it, the node moves only when those 40 pt do not fit. Like
`keepWithNext`, it stops at a node with `break`: the content from that node on
starts a new page, so it never counts.

## Floats

A figure that may move away from its paragraph gets `float`. Here each figure
goes to the top of the column that holds its place in the text, and the text
flows on around it:

```vue
<template>
  <PdfView class="body">
    <PdfView v-for="section in sections" :key="section.id" tag="section" :bookmark="section.title">
      <PdfText class="h2" keep-with-next>{{ section.title }}</PdfText>
      <PdfText v-for="paragraph in section.paragraphs" :key="paragraph">{{ paragraph }}</PdfText>
      <PdfView v-if="section.figure" tag="figure" class="figure">
        <PdfImage :src="section.figure.src" alt="" />
        <PdfText class="caption">{{ section.figure.caption }}</PdfText>
      </PdfView>
    </PdfView>
  </PdfView>
</template>

<style>
.body {
  columns: 2;
  column-gap: 18pt;
}
.h2 {
  font-size: 14pt;
  font-weight: 700;
}
.figure {
  float: top;
  margin-bottom: 12pt;
}
.caption {
  font-size: 9pt;
}
</style>
```

When the figure does not fit at the top of that column next to the text
before its place, it waits for the next column, and the text after it fills
this column. A float never moves to a column before its place, and figures of
one side keep their order. Use `float: bottom` for the bottom of the column.
Without columns, the float goes to the top or the bottom of the page.

A wide figure spans both columns with `columnSpan: 'all'`. It goes above the
columns on the page of its place, or with `float: 'bottom'` below them, and
the text runs on in the columns:

```vue
<PdfView tag="figure" :style="{ float: 'top', columnSpan: 'all', marginBottom: 12 }">
  <PdfImage :src="chart.src" :alt="chart.alt" />
  <PdfText class="caption">{{ chart.caption }}</PdfText>
</PdfView>
```

Column figures and wide figures keep one order: on a page the wide top
figures come first. The [styles reference]($docs.styles#floats) lists the
`float` key and what fails.

### How floats are placed

The layout places floats area by area, in source order. An area is the
column a float stands in, the part of its column container on the page when
the float has `columnSpan: 'all'`, or the page content area without columns:

- A float goes to the area that holds its place in the flow, when it fits
  there next to the content before its place. Otherwise it waits for the next
  area of its page or column container, and the text after it goes on in this
  area.
- A float never goes to an area before the area of its place, and it never
  goes before an earlier float of the same side.
- At the start of an area, the floats that wait go first, as long as they
  fit. An area can hold floats only.
- For the flow, a float is not there: `keepWithNext` on a heading right before
  a float keeps the heading with the content after the float.
- A float does not split. It keeps the width it has at its place in the flow.
  The container's `gap` or `rowGap` spaces it from the flow, as any other
  child.
- A float can stand inside plain views, such as a `section` view in the
  columns. The layout splits these views at the float as at a page break: the
  first part keeps the top edges, the `id` and the bookmark, and the last
  part the bottom edges.
- The note of a `PdfFootnote` inside a float goes to the page where the float
  prints. A float whose note does not fit on the page waits for the next
  page, as a float that does not fit. An `id` on a float points to the page
  where the float prints, and the outline and the structure tree keep source
  order.

A float with `columnSpan: 'all'` in a column container, or a float inside a
plain child with `columnSpan: 'all'`, spans all columns:

- A top float goes to where the container starts on the page of its place. A
  bottom float goes to the page end while the container goes on to the next
  page. On the page where the container ends, it goes right below the columns,
  or to the container's bottom when the container has a `height`.
- The columns run on below or above it: it does not end them, as a child with
  `columnSpan: 'all'` in the flow does.
- The spanning floats and the column floats of a container keep one order per
  side. On a page, the spanning top floats come above the column top floats,
  and the spanning bottom floats below the column bottom floats. So a spanning
  float waits for a later page while an earlier column float of its side
  waits.
- A page with `columns` is a column container too: its spanning floats go to
  the top or the bottom of the page.

## Page tokens

```vue
<PdfText fixed>
  Page <PdfPageNumber /> of <PdfPageCount />
</PdfText>
```

Put `PdfPageNumber` and `PdfPageCount` in a `fixed` text to print them on every
page. A `PdfText` inside a `fixed` `PdfView`, such as a footer row, also
repeats; it needs no `fixed` of its own:

```vue
<PdfView fixed :style="{ flexDirection: 'row', justifyContent: 'space-between' }">
  <PdfText>{{ company.name }}</PdfText>
  <PdfText>Page <PdfPageNumber /> of <PdfPageCount /></PdfText>
</PdfView>
```

While pages are made, a `PdfPageNumber` or `PdfPageCount` keeps room for as
many digits as the page count has, each as wide as the font's widest digit.
The real number is painted into that room afterwards, placed by the text's
alignment, so a number never moves a line or page break. Because the room is
the same on every page, a line can break earlier than the real number needs:
on page 8 of 23 pages, a number keeps room for two digits.

A page token is a component, not a value, so it cannot go into a computed
string. Keep the computed part in a template expression and put the token
after it:

```vue
<PdfText fixed>{{ parts.join(' · ') }} · Page <PdfPageNumber /></PdfText>
```

A `PdfText` that holds `PdfPageNumber`, `PdfPageCount` or `PdfRunningText` can
contain only text and page tokens, and it cannot be nested inside another
`PdfText`. `PdfPageRef` has no such limit. A `PdfPageNumber` in a `PdfLink` goes
into a `PdfText` inside the link, and that link stays outside any other
`PdfText`:
`<PdfLink><PdfText>Page <PdfPageNumber /></PdfText></PdfLink>`.

```vue
<PdfLink :href="`#${section.id}`">
  <PdfText>{{ section.title }} <PdfPageRef :to="section.id" /></PdfText>
</PdfLink>
```

`PdfPageRef` resolves to the page where the destination starts, also when the
section spans several pages. The `to` id must match an `id` in the document, or
the render fails with `PDF_TREE_INVALID`. A document with `PdfPageRef` uses at
least two layout passes; `maxPasses` in [definePdf]($docs.define-pdf) bounds
them. See [Contents, links & bookmarks]($docs.contents-links-bookmarks).

A `PdfText` with `running` sets a value; `PdfRunningText` prints it in a
`fixed` header or footer:

```vue
<PdfText fixed>
  <PdfRunningText name="chapter" />
</PdfText>
<PdfText tag="h1" running="chapter">Methods</PdfText>
```

A page shows the value set by the node at its very top, otherwise the last
value set before the page. The value is the plain text of the setter, with
its nested texts and with spaces joined, or the `text` of `{ name, text }`.
A `PdfTableRow` also takes `running`, as `{ name, text }` only. `at` picks
another value of the page:

| `at` | Prints |
| ---- | ------ |
| `'top'` (default) | The value set by the node at the very top of the page, otherwise the last value set before the page. |
| `'before'` | The last value set before the page, such as a subtotal carried forward. |
| `'end'` | The last value set on the page, otherwise the last value set before it, such as a subtotal carried over. |

While a page is filled, its `'end'` value is not known yet. A fixed node that
prints it keeps the room of the value of its name that needs the most room.
When an `'auto'` table column is measured, `PdfRunningText` takes the longest
value that a setter of its name sets, counted in characters.
See [Carried subtotals]($docs.recipes#carried-subtotals).

These fail with `PDF_TREE_INVALID`:

- a setter that is `fixed` or in a `fixed` node, such as a header or a
  `PdfTableHeader`: it would set the value on every page;
- a setter in a footnote note, or on a `PdfText` nested inside another
  `PdfText`: put `running` on the outer text;
- a page token or a `PdfFootnote` inside a setter;
- a `running` value that is not a name or `{ name: string, text: string }`,
  a `running` name without a text on a `PdfTableRow`, a `PdfRunningText`
  without a `name`, and an `at` other than the three values;
- a `PdfRunningText` outside a `fixed` node, in a footnote note or in a
  nested `PdfText`;
- a `PdfRunningText` whose `name` no `PdfText` or `PdfTableRow` in the
  document sets;
- a `PdfRunningText` with `at="before"` or `at="end"` in a column of a column
  container: those values belong to the whole page, and a fixed node in a
  column repeats in every column.
